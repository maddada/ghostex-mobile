# ghostex-mobile Architecture

One React Native (Expo, New Architecture) app for iOS + Android. The UI, session inventory, machine management, and orchestration are shared TypeScript. Only two things are native per platform:

1. **The terminal surface** — iOS: Ghostty `libghostty` (ported wrapper from the VVTerm fork). Android: Termux `terminal-emulator` + `terminal-view` (copied from the Android fork).
2. **The SSH transport** — iOS: libssh2 (ported `SSHClient` subset from VVTerm). Android: SSHJ + BouncyCastle (ported `GhostexSshTransport` from the Android fork).

**Golden rule: PTY bytes never cross the JS bridge.** The SSH shell channel is piped into the terminal engine entirely in native code. JS only orchestrates: connect, run non-interactive commands (`ghostex sessions --json --mobile-summary`), open/close terminals, send discrete keys/text, receive lifecycle events.

Sent chat prompts use content-sized message bubbles. Markdown list bodies keep their intrinsic width while
remaining able to grow and shrink, so an ordered-list prompt contains its words and inline pictures. A list
item whose first paragraph starts as a row of words and pictures draws its marker in that row, before its
first words, as the desktop does; a filmstrip in an agent's reply keeps its marker beside it.

Chat pill sheets belong to `NativeChatScreen`, not the composer: a live question may replace the composer while
a sheet is dismissing. On iOS, a Subagents or Resources pick opens its destination from the sheet's native
dismissal callback, not a timed delay. Android dispatches the pick immediately.

### Project file previews

`DocsScreen` opens a Ghostex page as its page in the Web preview (`openComputerPage` in `src/docs/openComputerFile.ts`,
as chat file links do) and every other project file in `DocViewerScreen`, also used by chat and terminal file links.
`src/docs/page.ts` (`buildDocPage`) applies the browser's existing preview policy when Files supplies a size:
Markdown and HTML render up to 2 MB; other UTF-8 text opens as numbered source with JavaScript, asset loading
and annotations disabled. Images, binary files and files over the limit show their name, kind, size and full
path instead, with Copy Full Path and Share below the metadata and only Reload in the header. Reload measures
the project file again before choosing its mode. The viewer owns loading, cancellation, failures, retry,
clipboard feedback and sharing for all three modes. File links outside Files keep their existing text,
image and media previews and limits.

## Native module contract (`modules/ghostex-native`)

Both platforms implement this API, except the iOS-only bar layout functions and event (`observeBarLayout`, `stopObservingBarLayout`, `onBarLayoutChange`) and the iOS-only file share sheet (`shareFile`), which the shared layer calls only behind `Platform.OS === 'ios'`. TS bindings in `modules/ghostex-native/src/index.ts`.

### Concepts

- **machineId** (string): key for one SSH client connection (multiplexed channels). Reconnecting with new config replaces it.
- **sessionKey** (string, JS-chosen, e.g. `${machineId}:${sessionId}` or `${machineId}:tab:${uuid}`): key for one _terminal entry_ in the native registry. An entry owns: terminal engine instance + SSH PTY shell channel. Entries survive view unmount (warm sessions); JS enforces the max-7 warm policy by calling `closeTerminal`.
- **GhostexTerminalView**: native view with prop `sessionKey`; mounting attaches the view to the registry entry (rendering + touch + IME input). Unmounting detaches without killing the entry. One entry is shown in one view at a time (a second view for the same key takes it over), so two panes always show two different sessions.

### iPhone Duo chrome (iOS, built with the iOS 27.1 SDK)

The app uses the whole window on the Duo and draws its own header controls next to the status items.

- **Vertical bar disabled app-wide.** `GhostexRootViewController` (`modules/ghostex-native/ios/`, supplied to Expo through the public `ExpoReactDelegateHandler`, registered under `reactDelegateHandlers` in `expo-module.config.json`) answers `preferredVerticalBarBehavior = .disabled` from the first frame, so the status items stand in one row along the top in every pose. Controllers presented over the root (React Native `Modal`, `Alert.alert`) would otherwise flip the status items into a column while shown; `StatusBar.setVerticalBarBehaviorIOS('disabled')` in `index.ts` is Expo's own switch for them (it swizzles `UIViewController.preferredVerticalBarBehavior` inside `expo-status-bar` 58.0.4, the one swizzle the app accepts, for exactly this mechanism). Both are no-ops before iOS 27.1.
- **Placement.** `headerPlacement` (`src/components/common/verticalBar/layout.ts`) reads the reported bar layout: `band` where the system's top bar region lies inside the top safe-area inset (beside the status items), otherwise `top` (the screen's own header under the status bar, as on every other iPhone). The side bar placement (`rail`) stays compiled for a system that stands a vertical bar, but with the bar disabled it is unreachable on the Duo.
- **Band overflow.** Header buttons that do not fit the band row move, last first, into the screen's "More options" menu (`bandSplit`, `useBandOverflow`); Back and "More options" stay. Terminal, Web Preview and the stack header (`StackHeader`) use it.
- **Settings** show two columns when the chrome is in place and the content width holds a 320 pt list and a 375 pt page (`twoColumnWindow`); otherwise one column, at most 640 pt wide.
- **Fold.** Divisions are read natively with `reservedRegions(kind: .division, options: .includeInactive)` and delivered in `BarLayout.divisions`. The band and anchored menus keep off them (menus off the active ones only).
- **Laptop pose.** An active division wider than tall is the laptop pose (`laptopFoldOf` in `layout.ts`; `useLaptopFold` in `verticalBar/laptopFold.ts`, provided by `VerticalBarArea`); a book-pose or inactive division gives none. Gated on it: the terminal and the Befehlspad (`components/terminal/laptopMode.ts`: output above the fold, keyboard up or not, the floating pad in the upper half with its own stored place, the open pad's room reaching below the fold only where the upper half is too short for it even over the header, layers below the fold in the keyboard's place, the text editor above the fold), the chat view above the fold, keyboard up or not (keyboard down: the view ends above the fold, `foldUpperHalfInset`; keyboard up: the composer lifts above it), the keyboard-avoiding layer treating the fold's top as the cover's top (`laptopCoverTop`), sheets starting below the fold and centred cards below or above it, held to that band with longer content scrolling inside, in the window or in the frame of the area they cover (the chat's account-switch card; `components/common/foldAvoidance.ts`), the page sheet's, Web Preview's, Docs viewer's and project file view's content (with its loading and failure states) ending above the fold (`foldUpperHalfInset`; the two stack screens read their area's bottom in window points), and lists kept off the fold, so no row is drawn on it at rest or while scrolling (`FoldListFrame` in `components/common/foldGap.tsx`, from the frame measured in the window). A `FlatList` whose rows take their state from the screen or a store runs across the fold: the list fills the frame down to the fold's top, and a copy of it, hidden from VoiceOver and without pull to refresh, fills the frame below the fold's bottom and follows its scroll (a drag on either moves both, on the JS thread, so during a fast fling the lower part trails by a frame or two); content leaving the upper part at the band appears at once below it, and the band adds no scroll distance (`foldListAcross` and the offsets in `layout.ts`; adopted by the Sessions screen's classic list in `sessions-screen/session-list.tsx`, the work-link picker and the Files browser). A scroll view page, and a list whose rows keep state of their own, end above the fold and the lower half stays empty (`foldUpperHalfInset`; adopted by Settings pages, the attention list and, through `endAboveFold`, the Sessions screen's Unified list, whose cards keep their swipe state), as a running list does while the keyboard is up or while its content fits above the fold. Development builds show the division read in Settings > Advanced > Debug.

### Error codes (rejections carry `code`)

`E_AUTH_FAILED` · `E_HOST_KEY_MISMATCH` · `E_UNREACHABLE` · `E_REFUSED` · `E_TIMEOUT` · `E_NOT_CONNECTED` · `E_CHANNEL_FAILED` · `E_SFTP_FAILED`. ### View

```tsx
<GhostexTerminalView
  sessionKey={key}
  style={...}
  onSingleTap={() => ...}   // optional: show keyboard
  onCaretChange={({ nativeEvent }) => ...}   // iOS only: { top } of the cursor row, points from the view's top
  paneFocus={true}          // iOS only, two panes only: the active pane's terminal (cursor filled) or not (hollow)
/>
```

Native view responsibilities (per platform, matching current apps):

- Rendering + scrollback scrolling (iOS: synthetic wheel events w/ momentum per spec §4; Android: Termux TerminalView built-ins).
- IME/soft-keyboard text input directly into the engine (view is the text-input responder).
- Pinch-to-zoom → font size ratchet (±1pt at 1.12/0.89 thresholds) + native HUD ("N pt" / "Font Size") per spec §3, then emit `onFontSizeChange` for JS persistence. Range 4–32, default 13 on every platform.
- Touch text selection (both platforms keep their existing native implementations).
- Scroll-to-bottom on output/keypress (engine behavior; respect autoScroll setting via prop later).
- Cursor row (iOS): `onCaretChange` fires with the top edge of the cursor row (`y - height` of Ghostty v1.3.1 `imePoint`, whose `y` is the cell's bottom) after a draw when its whole-point value changed, and once when the view is attached to the host (`GhosttyTerminalView.reportCaretIfNeeded`). The terminal screen slides the view by it with the keyboard (`docs/specs/terminal-screen.md` §2 "Keyboard: the terminal slides"); the view's own size, and so the grid, does not change with the keyboard. Declared in the iOS module's `Events(...)` and typed in `GhostexTerminalViewProps`; the Android view declares none and JS does not pass the prop there.
- Pane focus (iOS): `paneFocus` sets the Ghostty surface's focus for a terminal in a pane, `true` for the active pane (Ghostty draws its cursor filled) and `false` for the other (hollow), whichever view holds the keyboard; a pause takes the focus as before and resuming gives the pane's back. Left out (one terminal on screen) the surface's focus follows the first responder as before (`GhosttyTerminalView.paneFocus`, `GhostexTerminalHostView.setPaneFocus`). JS passes it only on iOS and only with two panes.

### Keyboard accessory: the Befehlspad on iOS, the "2 rows of keys" bar on Android

On iOS the floating pad (`components/terminal/CommandPad.tsx`, state in `useCommandPad.ts`, key logic in `terminalKeyInput.ts`, keys in `commandPadKeys.ts`, geometry and the user's place in `commandPadLayout.ts` (stored per layout as `commandPadPosition`, `settings/commandPad.ts`), layers in `CommandPadLayer.tsx`, editor in `TerminalTextEditor.tsx`) replaces `TerminalKeyBar.tsx` and the floating Upload button; behaviour per `docs/specs/terminal-screen.md` §2 "Befehlspad". Android keeps `TerminalKeyBar.tsx` as before the pad. The paragraph below describes the rows (the key bar's, and on iOS the pad's Keys layer) and the editor.

Both renderers use the same input machine (`terminalKeyInput.ts`, wired to native events, platform haptics and the key haptics setting by `useTerminalKeyInput.ts`), extracted from the key bar. Modifier latching and native sync, repeat timers, custom text actions and agent sequences live there; the bar, pad and layers keep their rendering and gestures. Text actions, sequences and Paste spend one-shot modifiers in both the rendered state and the native keyboard while keeping locks, so the following software-keyboard character cannot inherit a spent modifier.

Rendered in **RN** (the rows in `components/terminal/TerminalKeyBar.tsx` and `CommandPadLayer.tsx`), not a UIKit inputAccessoryView, which keeps it cross-platform. On iOS the pad's text editor stands in `KeyBarDock`, which moves with the keyboard (`useKeyboardMetrics`: a layout animation approximating the keyboard's measured motion (spring on show, ease-out on hide; `keyboardMotion.ts`; Fabric has no keyboard curve) and at once with Reduce Motion on) instead of appearing at once; on Android the key bar stays in the layout flow. Discrete keys go through `sendKey` (low rate, bridge OK). Layout/behavior of the rows per `docs/specs/terminal-screen.md` §2: default rows [Esc, Shift, NEWLN(Ctrl-J), Home, ↑, End, PGUP] / [Tab, Ctrl, Alt, ←, ↓, →, PGDN], one-shot modifier latching, repeat-on-hold (350ms then 50ms) for arrows/home/end/page keys.

## Two panes (iPhone Duo inner display, `src/panes/`)

An agent session (its terminal or its chat view) beside a second session, the Web Preview, the project's Files, the computer's agent sessions, the project's Git Changes, the computer's account usage or the attention list on the terminal screen; behaviour per `docs/specs/terminal-screen.md` §7.

- **When.** Only where the window has the fold's divisions (the Duo's inner display; read from `BarLayout.divisions`, so the window decides, not the screen), on iOS, with an agent session (attach tab) selected, in the terminal and in the chat view. Folded, on other iPhones, on Android, for a shell tab and while a question opened from the attention list or by a link stands the screen is unchanged: one content area, and the stored layout waits. A question's link (`deepLinks.ts`'s `showChatView`: a notification, the Notifications screen, the attention list) sets `usePaneStore`'s `questionHold` (in memory only); while its session stays selected in its chat view the terminal screen offers no panes, but shows the Panes button (not behind a question from the attention list, `PaneQuestion`), which releases the hold and shows the panes that waited, or opens them as the Panes button does. Side by side (`sideBySide`) when wider than tall and in the laptop pose, one above the other (`stacked`) otherwise.
- **Selection and the active pane.** The pane tapped last is the active one (`usePaneStore`'s `activeSlot`). A session pane that becomes active holds the terminal store's `selectedSessionKey`, so the keyboard, the pad, the text editor, Upload and the menus reach it through their existing paths; a pane without a terminal becomes active without changing the selection, which stays in the session pane, and the queued-prompts pill stands in the selected session's pane (`selectedPaneSlot` of `useTerminalPanes`). The keyboard follows the active pane however it changes, and goes to the terminal left alone on screen when the active pane or the selected tab closes: `useTerminalPanes` hands it to that terminal (`focusTerminal`) once it is open, while the keyboard is up and the text editor closed. A non-terminal pane becoming active takes it from the terminal (`blurTerminal`); from a field of such a pane it comes back the same way, to the terminal that becomes active or to the session left alone when either pane closes, never when the Duo folds (the pane's content opens full screen) or to a session that was not on screen. A hardware keyboard needs no software keyboard over the app, so with no keyboard frame `useTerminalPanes` moves the typing by the same rules when it is held: by a text field of the app (`TextInput.State.currentlyFocusedInput()`: the chat's composer, a pane's search field) at once, or else as the native side answers (`keyboardInputHeld`, `KeyboardInputHolder` in `GhostexNativeModule.swift`: the key window's first responder is a terminal outside its edit-menu-only focus, or another text input such as a field of the Web Preview's page while `GCKeyboard` reports a connected hardware keyboard); a counter (`keyboardRequest`) drops an answer that a newer question, a change of the active pane, the text editor or the keyboard superseded. A lowered keyboard resigned its holder, so nothing comes up. The other session pane's session is `paneSessionKey` in `src/terminal/sessions.ts`: the warm-session policy never evicts it (nor the selected one), closing the selected tab hands it the selection, and foreground restore attaches the selected terminal first, then it. A session opened from a pane (a pick in the chooser, a row of the agents pane or the attention list; `openPaneSession` in `useTerminalPanes`) marks the session on screen as `paneSessionKey` before it selects, so the eviction it may cause never closes it; `usePaneHost` sets the key again on every selection change. `zmxDisplay.ts` counts both as visible (each announces its own grid; neither is pinned to the off-screen width) and `sessionOnScreen` checks both.
- **Modules.** `layout.ts` reads and writes the stored layout (`panes.layout.v1` in AsyncStorage, exactly the stored layout's format version 1, with `closed: true` while the panes are closed; anything else, or one session in two session panes, is discarded and one pane is used), `divider.ts` clamps the divider to 25-75 %, `geometry.ts` places the two cards, the divider handle and the title bars and applies the keyboard rules (nothing of them is stored) and, half folded like a book (an active division down the window, from `BarLayout.divisions`), keeps the handle, the title bars, the selected session's queued-prompts pill and the controls of a non-terminal body (`controlInsets`, handed to the body as `PaneFrame.controlInset`; its content may run across) off the fold without moving the cards, `resolve.ts` decides what each slot shows from the stored layout, the chooser, the panes that came along when the window turned and the selection, and how a stored layout opens without a session it showed before (`openedSlots`: the session on screen in its first session pane's place, the other pane types and the divider as stored, the chooser in place of a second session), `store.ts` keeps the layouts, whether the panes are closed (closing keeps every shape's layout and `panesFrom` hands the resolver neither a layout nor the panes that came along while they are closed; the Panes button's `openPanes` opens them again through `openedSlots`, and `panesFrom`'s `turned` has the resolver open a stored layout the same way when the window turns into its shape while panes are on screen, the chooser it opens then held in the store by `usePaneHost`), the pane tapped last and the panes last on screen, `usePaneHost.ts` keeps it in step with the terminal store, `useTerminalPanes.ts` is the terminal screen's pane controller (a touch, a pick, the chooser's Close row and its new terminal (`createSessionCommand` through `runGhostexCli`, then the pick's `openPaneSession`), the Panes button, the keyboard following the active pane, Back from a question opened in the attention list, the active pane's content full screen when folded; `paneLayoutInput` maps the terminal area, the keyboard, the editor and the fold to `paneGeometry`'s input), `PaneHost.tsx` draws the cards, title bars, divider and swap, `PaneContentView.tsx`, `SessionPane.tsx`, `SessionChooser.tsx` and `AgentsPane.tsx` the bodies (the chooser's Add project pushes the existing `AddProjectSource` route), and `paneTypes.tsx` lists the pane types this build shows (the chooser and the title menu read it). `initPaneLayouts()` (from `App.tsx`) loads the layouts once the saved computers are loaded (their load can merge two records of one computer and move what was saved under the dropped id, the layouts' sessions included, to the one it keeps) and ends a layout whose session pane's tab closes.
- **Gestures.** Only a pane's title bar (swap drag; not while the chooser is one of the two panes, which is never stored) and the divider handle (resize) take a touch; a pane's content never does, so the terminal's own selection, scrolling and pinch stay as they are. While a title bar is dragged, its copy follows the finger through an `Animated` offset (`PaneHost`), so the host's state, and with it the panes' bodies, changes only when the finger crosses into or out of the other slot; the divider drag resizes the panes live, the finger's newest position taken once per frame (`requestAnimationFrame` in `PaneHost`'s `Divider`), and the release or a lost touch goes through the same frame (the released position is stored and the drag cleared together then; a new drag or the divider going away before it stores the position at once; a lost touch clears the drag without a position, so nothing is stored and the panes show the stored position again), and a terminal view keeps the size it had when the drag started until that frame (`PaneHost` hands the bodies the drag's starting geometry), so it is handed at most one new size per drag (none after a lost touch) and its grid, and the computer's terminal, are resized once; `PaneBody` draws a body again only when what it reads changes: a terminal its size and cover, every other body only whether it is active and its fold inset, so a resize alone leaves it to layout. A swap changes only the cards' frames; the terminal views keep their place in the view tree and are not mounted again.
- **Chat in a pane**. A session pane shows its terminal or its chat view; no pane type and no stored field carries it. `usePaneStore`'s `chatSession` (in memory only) names the one session whose pane shows its chat, `resolve.ts`'s `paneChatAfter` keeps it in step (a session coming into the panes from outside shows its saved view, a pane's pick, marked as `pickedSession` by `openPaneSession`, its terminal; a saved view changing on screen takes effect; the panes' own choice otherwise holds) and `usePaneHost` returns it as `chatSessionKey` (a session that has a chat view, `tabChatCapable`) with `setChatSession` for the header's view button and the chat's Terminal View. `usePaneHost` also sets `usePaneStore`'s `paneViews` (in memory only, null with one content area): what each session pane on screen shows, chat or terminal, which Files' Add to Session Context (`sessionInputs.ts`) follows before the session's saved view. The terminal screen renders that chat (`NativeChatScreen` with `inPane`, keyed by session) as the pane's body through `PaneContentView`'s `chat`; its own hidden chat of the selected session is not mounted for that session, so one chat core never has two screens. With two panes the screen keeps the terminal's keyboard handling (`slidesWithKeyboard`, the laptop fold) whatever the active pane shows; `chatPlacement.ts` tells the chat it stands in a pane, so the composer's frame lifts nothing (`KeyboardLiftedView`), the composer takes its compact form (`NativeComposer`: the model pill alone through `OptionPills`' `modelOnly`, More actions, Dictate and Send; no pill strip, toolbar controls, Copy Report or status line, no footer fit sent to the core, and `moreActionsRows`' `allFolded` lists the controls and option settings as overflowed ones; `LoneScrollBottom` carries the ↓ there), and the cards band, the question card and the other in-flow cards, tables and lone pictures are sized by the chat's own frame. ## Agent notifications and the attention list (`src/notifications/`)

Local notifications while the app runs, push while it does not (gxserver on the computer → Expo Push Service → APNs, once the build carries its push project and the APNs key is in Expo), and the attention list: what needs the user now, one row per session by its live state (Needs you from the computers' session lists; Done and Failed from the unread rows of the computers' notification feeds, whose read state the phone shares with the desktop bell; account notices last), not the event history the desktop bell keeps. While the app runs out of front (in the background, or inactive), a computer that confirmed it accepted this phone's push registration (known across launches) notifies by its push only; every other computer keeps the app's own notifications, also one whose registration has no answer yet or whose confirmation was lost with the stored record. Push is best effort and only reaches the phone while gxserver runs, so the list is the reliable view after a reconnect.

- **Wiring.** `feedStore.ts` and `pushStore.ts` are the modules that touch the app: `initAttentionNotifications()` (called once from `App.tsx`) runs the one-time permission ask, installs the tap handler and starts one `FeedEventSource` for the app's lifetime; its zustand store (`feeds` per enabled computer, iOS `permission`, `pushComputers`: the computers that confirmed they accepted this phone's push registration, as the record of announced events keeps them across launches, null until that record is read; `closed`: per computer the sessions its closed-session list holds, read for the list, the last good read kept through a failed one; `restores`: restores of ended sessions under way or failed) feeds the list and Settings. `initPushNotifications()` (called right after it) registers the push token and the background task (below). Whenever a read brings a session row that is new or changed its kind (also on a first read and with notifications off), and on an explicit refresh (the list comes into view or is pulled, the app comes back) when the feed has a `needsInput` row or the session list was not read yet, the computer's session list is read again (`refreshMachineFresh`), so the list's join ("has a question", agent, project) is current; polls alone do not read it. A session-list read serves only feed rows that arrived before it started; rows that arrive during it wait for one more read after it. On an explicit refresh, once the session-list read that refresh brought about for a computer whose feed answered has come (`refreshSessionList`; the refresh itself is done with the feed read and does not wait for it), that computer, when its Done or Failed sessions that list does not hold (`endedCandidates`), also has its closed-session list read (`fetchClosedSessions`, the Sessions search's: up to five `ghostex previous-sessions` pages of 80 over SSH, once per computer and refresh, never on the feed's poll), so a session the fresh list no longer holds is checked in the same refresh; only that list makes a row Ended, since the session list also leaves out live sessions of inactive projects. A failed read keeps the last list read (with none, no row is Ended) and leaves a log line; the kept list also stays while the computer cannot be reached or its session list is not read, and goes once the computer has no candidates any more or leaves the enabled computers.
- **Reading the feed.** Over the warm link to the computer's gxserver: `POST /api/readNotificationFeed`, changes through `POST /api/updateNotificationFeed` (`markRead`, `markUnread`, `dismiss`; `markRowsRead` sends one `markRead` per row) (`feedClient.ts`). `eventSource.ts` reads every 5 s, every 30 s while a computer cannot be read; a computer whose `ghostex server endpoint` lists `notificationStream` announces changes on `/api/events?stream=notifications` (`feedStream.ts`) and is read on each announcement, otherwise every 60 s. That channel is open only while its computer is shown and the app is in front, one per computer: hiding or removing the computer, or the app going to the background, closes it, also while its forward is still being looked up, so the lookup's answer opens no channel then (`ensureStream` in `feedStore.ts`). A computer without the feed on the phone's route shows a notice in the list (`legacy`). `feedContract.ts` is the trust boundary: it keeps a row's message text (`body`) only for the attention list's card body, as the desktop's bell shows it; no notification, Live Activity, persistent notification or log line carries it. Failures go to the app log as a fixed word (`refused`, `unreadable`, `legacy`, `unreachable`, `unexpected`), never the computer's or iOS's error text.
- **From row to notification.** An unread row is a new event when its id was not there at the previous read or its kind changed (the host turns a session's unread `finished` row into `needsInput` in place); a row only marked read or unread again is none. While the app runs, new rows notify; while it is out of front (in the background, or inactive), a row of a computer in `pushComputers` posts nothing of its own, because that event's push announces it (Push, below). Each read keeps the stretch in front it began in, so this also holds for a row read in front whose session list still waited when the app left the front (also when the app is back in front by then). That is judged once the stored record of announced events is read, so a computer whose confirmation an earlier launch stored counts from the first moment of a launch; a computer the record holds no confirmation of (no answer yet, a refusal, or a stored record that could not be read or is missing) keeps the app's own notification. The first read of a computer, the first after a failed one, and the first read after the app comes back from the background (from the first app state after `background`; iOS returns through `inactive`) only record what is there. Back in front from inactive without a background phase, every computer is read again at once (a read still under way is dropped, `readAgain`) and every row that read brings counts as read out of front, also one written after the return before that read answered; every later read is in front again, also while the stored record is still read. A read still under way when the app starts returning from the background is dropped, so it neither notifies nor counts as that first read. `notify.ts` (`processHostEvents`) maps it (`events.ts`): only sessions in that computer's session list notify, only `finished`, `needsInput` (waiting, or "has a question" when the session has an open question card, `awaitingAnswer`, read only when the summary's `capabilities` announce it, or its `pendingQuestionCount` is above zero) and `failed` (written by the computer after its five quick retries of a transient error, at once for a permanent one or a program error, never on a user abort; the session's state is not read for it); then the Settings switches (`settings.ts`, `settings.v1` key `notifications`), none for the session open on screen (the app active and the focused Terminal screen showing its terminal or Chat View, `sessionOnScreen` in `src/terminal/zmxDisplay.ts`; its row stays in the list, and its event counts as seen, so a later copy announces nothing), and the gate of the record of announced events (`eventIdentity.ts`): one notification and one sound per event, within the rate limit (`rateLimit.ts`: one notification per session per 20 s, 8 per 60 s, counting every notification, every push iOS showed and every Sessions-list attention sound, kept across launches; a row's notification within 20 s after the attention sound of the event that named that row is part of that sound). The text is "agent · project" plus the event, never the agent's text.
- **One event, one notification, one sound.** `eventIdentity.ts` keeps the app's record of announced events, states its three invariants (an event gets at most one notification and at most one sound, across feed, live-channel, push and Sessions-list copies, delays, reordering and restarts, as far as its copies can be told apart; a first delivery is announced or held back by an existing rule, never dropped because the record is full or still loading; the record stays within its bound), the two accepted exceptions below and the identity contract the push route depends on, and is the one gate every announcing route goes through (`announce`): the feed's notifications and the pushes the app takes through `processHostEvents`, the Sessions list's attention sound through `announceAttentionTransitions` (both in `notify.ts`; `src/app/alerts.ts` calls the second). A push iOS showed itself goes in through `shownBySystem`, as a fact, not a request: its event gets its notification, and its sound only when the push carried one (`aps.sound`; the computer's pushes carry none, so the Sessions list's sound for that event is still to come, within the rate limit), whatever the switches, the session open on screen or the limit say now. An event is announced once any route made it seen or heard; a later copy gets only what it has not had yet (its notification, which carries the sound when the sound is still due, or the attention sound), each once. The record owns the app's one rate limit and stores its grants with the events. The limit counts what the person gets: every notification and every attention sound takes a grant, except a row's notification within 20 s after the attention sound of the same event, which the computer links by naming that row for the attention: that is the same announcement. Later than that, in the other order (the sound after a notification that came without it), and without that link, every part takes a grant of its own. A push iOS showed counts like a notification once the app learns of it: against its session's 20 s and the 8 a minute, also past them, also when its event was seen on screen or announced by the app already, once per presentation (the background run's second record of the same push counts nothing more), and as part of the sound when it is a banner within 20 s after its event's linked sound. So the Sessions list's sound for the event of a silent push, which normally comes in the same background run, is held back by that session's 20 s and stays silent; it plays only when the list shows the attention after those 20 s. What the limit or the switches hold back adds nothing (an event that already sounded keeps its sound), so a later copy brings it. A copy held back for the session open on screen makes its event seen (`seenOnScreen`): no later copy announces it, by notification or sound, also after the person left the session; seeing takes no grant and adds no announced event. The seen events are kept apart per computer as ids under the same identity: the row and kind (while the row is in the feed, or for two hours from when it was seen), or the row the Sessions list named until a kind of it comes; in the attention a copy provably came in, that attention's event of the kind (two hours), for a push without the row id; and the attention whose Sessions-list copy was seen, with the row that copy named, until the session leaves it or another attention of the session is seen. A seen copy covers only its own event: the Sessions list's copy covers its attention's later list copies and the row it named, never another row, and a row seen on screen does not cover a Sessions-list copy that named no row. At most 363 ids per computer (three for one event a minute over the window's 121 minutes); past that the oldest go first, so the worst case is one late notification or sound for an event the person saw, never a second announcement of an announced event. A feed row is the event: computer + session + row id + the host kind it entered (an in-place `finished` → `needsInput` is a second event of the row); it stays one event whatever the session list shows when it comes again. The Sessions list names no kind. From a computer that sends the feed row written for the attention (`attention.notificationId`, optional in the session summary, the same id a push carries) and announces it (`capabilities.attentionNotificationId`), the list's copy is that row's first event, exactly. From a computer that does not send it, or sends it without that flag (the id is then not used), the list's copy is an event of its own, its attention's: no row is matched to it, nothing is swallowed, and the sound and the row's notification are two announcements, each within the rate limit. Both count for the same session, so the one-per-session rule holds back the row's notification when it comes within 20 s after the sound; the app reads the session list before it handles a new row, so the sound normally comes first. With such a computer and the attention sound on, an attention event therefore usually brings the sound and its row in the attention list, but no notification, unless a later copy of the row comes. A push without `data.notificationId` is matched only within the session's attention it came in, as the event of the same kind there, never to the Sessions list's copy. A row joins an attention only when the session list read after it shows the session in attention since no later than the row was written. What is remembered rests on the host's push contract: gxserver sends each alert push once, at the event, with a time-to-live of at most 3600 s and never again, and a feed row can be read again only while it is in the feed. So the record keeps each announced event while its row is in its computer's feed as last read, and for two hours after its first announcement (the push's hour and an hour of margin), judged at the time a copy arrived, not when it is handled: while a copy waits (for the stored record, for the session list, while iOS pauses the app) the record forgets nothing it kept when the copy arrived. A push iOS showed is kept from when the app learned of it, however many arrive together. A Sessions-list copy that the named row's kind took over later is kept for two hours from that takeover instead, because the kind's event (a row turned into `needsInput` in place) and its push can come long after the sound; one that names its row is kept like that row's events. A session's current attention keeps its first event (the Sessions list's copy, else the first row linked to it) until the Sessions list shows the session out of it, because the list may see the session enter it late. The bound follows from the rate limit, since every first announcement the app made took a grant, and, for the events a push iOS showed started, from the computer's sending: it sends each alert push once and at most 8 a minute, a push lives at most an hour, and the app records it within the background run iOS starts for it (about 30 s, an assumption about iOS), so the pushes recorded within the window were sent within the window and the 61 minutes before it: at most 968 events from the window (8 a minute over the window's 121 minutes) and per computer at most 1448 events a push iOS showed started (8 a minute over 181 minutes), plus per computer the events of its feed's 40 rows, one per session in attention, and for events kept from a takeover within the window whose sound came before it, one per session plus one per row of the feed; the record checks it after every change and, should it ever hold more, keeps every event and logs it. Nothing is rejected for its age: a first delivery is always handled. The record is kept in AsyncStorage (`notifications.announced.v1`) across launches: ids, kinds, channels, times, whether a push iOS showed started an event, the rate limit's grants of the last minute, the ids of events seen on screen and the ids of the computers that confirmed they accepted this phone's push registration, never text and never the token; `initAttentionNotifications` reads it once the saved computers are loaded (that load can merge two records of one computer and move what was saved under the dropped id, this record included, to the one it keeps), and every notification and attention sound that arrives before it is read waits for it and then goes out in the order it came (a stored record that cannot be read is reported, and the waiting events are handled all the same). Two accepted exceptions. The app shows a notification or plays a sound first and writes the record right after: if iOS ends the app in between, the next launch does not know, so that event can be announced a second time but is never lost, the grants lost with that write let up to one more batch of other notices through in the minute after that launch, and a Sessions-list sound that a row's kind took in that moment can be taken by the row's next kind instead, which then comes without its own sound. And if the person changes the phone's clock by hand: set back, the record moves all its times back by as much as the latest of them lies ahead of the clock and stores that, so it forgets nothing early and the limit holds notices back for at most one more minute; set forward, an event can be forgotten early and announced a second time, and up to one more batch of notices than the limit allows can come in the minute after the change, for a change of any size (the phone's clock alone cannot tell a clock set forward from time that passed). A hidden computer keeps its record; a removed one keeps its events and the rows and kinds it saw on screen until their window ends (added again it is a new computer). A push without a row id outside its attention, or a copy outside the host contract (sent again, or later than an hour), is announced again: the push route sends `notificationId` for exactly one notification.
- **Posting and taps.** `notificationCentre.ts` is the only `expo-notifications` user (iOS only; local notifications and push: config plugin `enableRemoteNotifications` and `enableBackgroundRemoteNotifications` on, which adds the `aps-environment` entitlement and the `remote-notification` background mode; `plugins/withoutBackgroundFetch.js` takes out the `fetch` mode Expo's automatic expo-task-manager plugin adds, so `remote-notification` is the only one). A notification's `data` is `{kind, machineId, sessionId, url, notificationId}`; a tap opens `ghostex://session?machineId=&sessionId=` (`&view=question` opens the Chat View at its question card when the session has one; at a cold start the link waits until the saved computers, Settings and the terminal's saved views are loaded (`deepLinkStoresReady` in `src/app/deepLinks.ts`), then the session is attached and switched to its Chat View once the session list shows it, read anew right after the attach when it is not there yet; `src/app/deepLinkHandler.ts`) and marks the row read once the saved computers are loaded (at a cold start the tap comes before them). A tapped push carries `kind`, `machineId`, `sessionId` and `notificationId` without `url`: a `needsInput` push waits for the saved computers and reads the session's list anew (`openWaitingPush`). When that read ends within 5 s, the session opens once: the question link when the list shows a pending question by the rule of "has a question" (`awaitingAnswer` with its capability, or `pendingQuestionCount` above zero), else the plain link. When it does not, the session opens after 5 s (the question link when the list read before already shows a pending question, else the plain link), and the tap keeps its question intent: once the fresh list comes and shows a pending question, the question link follows and the Chat View with its question card replaces the view that opened, also while the app is inactive (Notification Centre over the session). A fresh list without a question or a read that failed (the computer cannot be reached) ends that wait without a further step. Any other push opens the plain link. Every opening of a tap (a notification of the app or a push; the first one and the question card) holds only while the tap is current: no later tap on any notification came, and the person has not left for another screen or session since the tap (`personNavigations` in `src/app/deepLinks.ts`: every navigation and every change of the Terminal screen's selected tab, except the first screen at launch and the app's own going to, or selecting, the tapped session, `tapOpens`). The link handler checks it at every step: at each retry while the stores load, inside the attach once an opening of the same tab already under way finished (before the terminal store selects the tab, `attachSession` in `src/terminal/sessions.ts`), once the attach is done (before it reveals the workspace, switches the view or navigates), once the session list is read, and when a navigation that waited for the screens runs. Otherwise nothing opens, and the question stays in the attention list and the session. A tap iOS reports twice (as the last response at a cold start and to the listener) is handled once. `firstAsk.ts`: the iOS prompt once on the first launch with notifications; Allow turns the master and the three switches on, Don't Allow leaves them off.
- **Push.** The computer sends one alert push per event, with content-available, whose `data` is `{kind, machineId, sessionId, notificationId?}` (identifiers only; `pushMessage.ts` reads it). Token (`pushToken.ts`, wired in `pushStore.ts`): with iOS's permission, the master switch on and a build that carries its push project (the EAS project id in the app config), the app fetches its Expo push token and registers it over the warm link with every enabled computer whose `ghostex server endpoint` lists `pushNotifications`, `POST /api/registerPushToken` with `{action: 'register', token, machineId, kinds, deviceId?}`, where `machineId` is the phone's own id for that computer (`MachineRecord.id`), which the computer keeps with the token and returns as `data.machineId` in every push, `kinds` are the Finished, Waiting and Error switches (`{finished, waiting, error}`; the computer pushes no kind that is off) and `deviceId` is the pairing device id of a computer paired by QR code (absent for one added by SSH, and an empty one counts as none; it lets unpairing the phone on the computer delete its token; a saved one the route's pattern does not take, 1 to 128 visible ASCII characters, is left out and the app log gets one line without the id, so the computer still takes the token and the switches but unpairing the phone there cannot find its entry, while Notifications off and removing the computer still remove it); at the start, back in front, when the master switch, the Finished, Waiting or Error switch or the first ask's answer changes, when a computer is added, shown again or paired anew, and when iOS issues a new token; a computer that took exactly what is wanted now (token, switches, pairing id) is not asked again. Without a push project, or when iOS or Expo give no token, nothing is sent and the app log gets one fixed line. A computer keeps one token per phone, under that phone's `machineId`, and replaces it at that phone's next registration. The master switch off sends `{action: 'unregister', machineId}` to every enabled computer (also once at a start with the switch off, since an earlier launch may have registered), on registers again. A change of the Finished, Waiting or Error switch sends a new registration, with the switches as they are then, once to each enabled computer that should hold the token (master switch on, iOS's permission, a push project; not one without the route or without `pushNotifications`, on the exec route or being removed), with no retry loop: a change that does not reach a computer takes effect there at the next registration it takes (its next occasion); the app in front applies the switches as they are, as for every notification. Removing a computer (Machines list or Edit machine, `unregisterBeforeRemoval` in `pushStore.ts`, called while its record and link still exist) first sends it `{action: 'unregister', machineId}` once the first ask was answered, hidden or not and whatever the master switch and the phone's token say, because an earlier registration may still be there; it waits for the answer at most `REMOVAL_WAIT_MS` (2 s), then the computer is disconnected and removed anyway: one that did not take the removal keeps the token, and nothing asks it again on its own (a second Remove confirmed during the wait asks it again); from the start of its removal no pass sends it anything for the rest of the launch, and none corrects it. The Remove confirm says that the computer stops sending push notifications only when the removal asks it; an open confirm follows the first ask's answer when it arrives (`useRemovalAsksComputer`, the same condition as `removalAsksComputer`). Hiding a computer sends nothing. A computer whose gxserver does not know the route (`notFound`) has no push; neither it nor one on the exec route (which cannot be asked) is asked again until the next start or token change; one that could not be reached is asked again at the next occasion. A computer whose endpoint does not list `pushNotifications` (read by the handshake that settled the warm link's route) gets no registration (`noPush`, nothing is sent), counts as not accepted, so Settings does not count it as one that can notify while Ghostex is closed, and is looked at again at the next occasion, so it is registered once its Ghostex lists the flag; what its link already knows (`offersPush` in `pushStore.ts`) is read at every occasion before each check that skips a computer (one without the route or on the exec route, kept until the next start or token change, and one holding what is wanted), so one that took the token and whose link settles an endpoint without the flag during the launch (a reconnect, also after the launch reached it only on the exec route) leaves at the next occasion without a request, and is registered anew once the flag is back (one kept as without the route or on the exec route at the next start or token change), while a link that has settled no endpoint says nothing; the master switch off and its removal still send it the `unregister`, since an earlier registration may still be there. What the person or iOS changed during a pass wins: a token fetched before iOS issued a newer one is never kept or sent, and the pass checks that the master switch and the token still ask for a request before it starts it and once more when the computer's route is known, right before the request is handed to the link (`superseded`); otherwise nothing is sent, the pass stops and the pass that follows sends what is wanted now (no retry loop); a switch change during a pass gets the pass that follows, which corrects each computer that took other switches. A request already handed to the link is not called back; the following pass corrects what it left, except for a computer whose removal started (no pass sends it anything). The record of announced events keeps across launches the ids of the computers that confirmed they took the registration (`pushComputers`, set only by a confirmed answer). An accepted computer stays while it cannot be reached, while it is on the exec route and when it does not take a registration or a removal (a computer keeps the token it holds until it takes a new registration or a removal); it leaves only when it removes the token, answers `notFound` or no longer lists `pushNotifications` (at the start, or at an occasion after its link settled such an endpoint); a removed computer's ids go with it, a hidden one's stay. Only a confirmation counts: a computer whose registration has no answer or was refused, or whose confirmation was lost with a stored record that could not be read, was not saved or is missing, counts as not accepted until it confirms again. The token is kept in memory only, goes nowhere but the computers' warm link, is never stored and never logged. In front or inactive (`takeForegroundPush` in `feedStore.ts`, for every push iOS asks the app about): the notification handler takes every push of a computer the phone has, so iOS shows none of it, and its event goes through `processHostEvents` with `notificationId` as the event id, like a feed row of the same event: one notification per event, one rate limit, the switches and the session open on screen as for any notification; a push the app cannot read or whose computer it does not have is left to iOS. Which of the phone's computers a push names (`pushMachineId` in `pushMessage.ts`): the enabled computer whose id is `data.machineId`, matched by that id only. Out of front (in the background, or inactive) the app posts no notification of its own for a row of a computer in `pushComputers`: that event's push announces it (iOS shows it in the background; while the app is inactive iOS may ask the app or show it itself, which is not verified); a row of any other computer keeps the app's own notification. In the background (`backgroundPush.ts`, the task defined in `pushStore.ts` when the module loads, since a launch in the background mounts no screen): the app loads the saved computers and Settings, refreshes the session list (`refreshAll`) once, then applies the list to the Live Activity and widgets (`updateLiveActivity`, `updateWidgets`) and awaits their native calls within 25 s. Both entry points install their existing consumers when a background launch mounted no screen; neither reads the summaries again. If the refresh fails or reads no computer, both stay as they are; a successfully read empty list still updates them. The task detects a read through the inventory store's `loadedAt`, which a failed read keeps; a push with an alert that came while the app was in the background was shown by iOS and goes to the record as its event's notification (`shownBySystem`, with its sound only when the push carried `aps.sound`), before and once more after the refresh, counted once, so a feed read later in that run does not announce it again. Back in front from the background, the first read of each feed only records what is there, so pushes iOS showed meanwhile are not announced again; back in front from inactive without a background phase, every computer is read again at once and what that read brings counts as read out of front, because iOS may have shown pushes meanwhile without asking the app, and a run then records nothing. Limits: a hidden computer keeps the token, also after Notifications are turned off, and can keep pushing (whether hiding should remove it is open); a computer that could not be reached at its removal keeps it until the token is removed on that computer; a computer that holds the token of an earlier registration but does not list `pushNotifications` counts as not accepted, so out of front its rows keep the app's own notifications and its push can come as well, until Notifications off or its removal removes the token; a registration a pass handed to the link before a computer's removal started is not called back and can reach that computer after the removal's unregister, which then keeps the token and can keep pushing until the token is removed on that computer; should removing the computer on the phone fail after the unregister went out, it stays saved but gets no registration until the app starts again; a second Remove confirmed during the removal's wait sends the unregister again and runs the disconnect and removal again; a change of the Finished, Waiting or Error switch that does not reach a computer (out of reach, no answer, refused) takes effect there only at the next registration it takes, so until then that computer can push a kind now switched off (iOS shows it while the app is not in front) and, for a kind now switched on, sends no push while the app posts none of its own for an accepted computer's rows out of front (they are in the attention list); a push that does not arrive while the app runs out of front leaves that event without its timely notification (its row is in the attention list); a notification the app showed in front can be followed by its own push when the app went to the background before the push came; a computer that took a registration the phone holds no confirmation of (its answer was lost, also when a later registration is refused; the stored record could not be read, was not saved or is missing) keeps the app's own notifications out of front, so its push can come as well, until it confirms a registration again; after the app's data is lost (deleted, or the app reinstalled) a computer added again gets a new id and, with its registration, a new entry on that Mac: the old entry is not replaced by registering again, and Notifications off and removing the re-added computer name only the new id, so the old entry goes only when Expo reports its token as no longer registered, when that phone is unpaired on the Mac (if it carried a pairing device id), or never if neither happens, and until then that Mac can push to the phone under the old id as well, which is left to iOS (shown, its tap opens nothing in the app; open, no cleanup is designed); a row written after a return from inactive that the first read after the return brings counts as read out of front, so for an accepted computer it posts nothing of its own and is announced only when its push comes (in front the app takes that push); and which of the two iOS does with a push while the app is inactive, and whether a run follows, is not verified on a device: the app covers both (a push it is asked about is announced once; rows such a computer wrote meanwhile count as read out of front, and a row of it read in front that still waited when the app left the front posts nothing of its own).
- **UI.** `attentionRows.ts` builds the list as a state inbox, one row per session: Needs you (every session of every enabled computer whose session list shows it waiting for the user, `waitsForUser`, the one waiting longest first, as approval, question or wait; ## Home Screen widgets (`src/notifications/`, `modules/ghostex-widgets/`)

Small, medium and large widgets (StandBy shows the small one) from a snapshot the app writes into the App Group; behaviour per `docs/specs/widgets.md`. No push: they show the app's last write and its data time.

- **Snapshot.** `widgetSnapshot.ts` (`buildSnapshot`) builds `widget-snapshot` version 2 from every enabled computer's summary with the Live Activity's classification (`candidateFor`, `compareShown` in `contentState.ts`): counts of working and waiting agents, the attention marker, up to eight agents waiting first, the data time (the oldest summary read), the usage bars when there are any. Each agent carries the candidate's resolved artwork and packed RGB tint; both widget lists pass them to the shared `AgentMarkView`, never resolve a display name. Older snapshot formats show the empty state until the next app refresh replaces them. No prompt, reply or title text.
- **Writer.** `widgetWriter.ts` (`createWidgetWriter`): after each session refresh writes the snapshot and asks WidgetKit for one reload, unless nothing shown changed (compared with the data time to the minute); writes nothing before the first summary; deletes the file when the last computer is removed. Usage: reads the selected computer's `agentAccounts` (`readAccountsAnswer`, `buildUsageBars`) while the summary poll runs, at most every 2 minutes per computer (also across switching computers), and leaves out bars older than 5 minutes or of another computer. `widgets.ts` wires it to the inventory and machines stores (`initWidgets()` from `App.tsx`, iOS only, the module optional); `updateWidgets()` installs that same writer when needed and applies the latest summaries after the background push task read them, awaiting the write and reload without another summary read.

  Widget usage reads ask the same `accountUsageColumns` core operation as the pane for window names, joined by input position before account filtering. The snapshot keeps the readable raw percent and absolute reset time; a window without a projected name is not labeled with a locally guessed name.
- **Native.** `GhostexWidgetsModule.swift` writes and deletes `widget-snapshot.json` in the App Group container (`Shared/GhostexWidgetStore.swift`, which the extension shares) and calls `WidgetCenter.reloadTimelines(ofKind:)`. The widgets (`ios/Extension`: snapshot decoding, timeline provider, SwiftUI per size) are compiled into the one WidgetKit extension `plugins/withWidgets.js` adds, beside the Live Activity, whose glyphs, agent marks and time parsing they reuse. The App Group comes from app.json's `ios.entitlements`; the extension's entitlements and both Info.plists (`GhostexAppGroup`) take it through the build setting `GHOSTEX_APP_GROUP`.

## App appearance

`src/theme/useAppearance.ts` resolves the saved app appearance and the desktop colour model for native pages, setup and machine forms, Files, Web Preview chrome, Voice, Usage, pane chrome, notification rows, the machine strip, bottom bar, menus, sheets and dialogs. Existing per-appearance style builders repaint their consumers; no separate screen palette or stored setting is used. The app navigator takes the same page, header and text roles. Session and pane terminals still receive their own palette/background through `useTerminalColours` and native settings sync; the laptop cover uses that terminal background too.

The model keeps the desktop surface calculations. `readableSecondaryText` moves text toward its foreground only as far as its drawn surfaces require; the app's primary foreground can move toward black or white where the existing neutral/destructive washes require it. The original muted glyph role remains separate. Chat uses its existing override and work-area surfaces, with readable text roles on those surfaces. Native Live Activity and WidgetKit extension colours are separate and unchanged. The desktop-specified optional sleeping-row dimming and Unified status colours remain in place; ordinary ink adjustment does not remove those visual states. Unrestricted custom terminal backgrounds retain the selected palette and desktop brightness split, including the foreground fallback when that split cannot reach the text-contrast target.

Generated Markdown, source, plain-text, image and media viewer pages take the native viewer's colour roles through their own theme stylesheet. An open generated page repaints its stylesheet without rereading the computer; escaped source keeps JavaScript disabled and repaints its inline HTML. Authored HTML and forwarded Web Preview sites retain their own page colours. Half folded like a laptop, Settings' preset scroller and mode-colour controls stay above the fold because the Interface page's shared Settings scroll frame ends there, and the palette and notice lists run across the fold, their rows continuing below the fold's band, each list in its own `FoldListFrame` (`components/common/foldGap.tsx`); each palette picker is one virtualized list rather than a scroll view containing every row.

## Defaults (from the Android app)

autoScroll=true · doneNotificationSound=true · refreshButton=false · fileUploadButton=true · keyboardButton=false · hideKeyboardOnStartup=true · Android terminal dark-only, background `#000000`. iOS terminal colours come from the theme settings (the desktop's defaults: GitHub Dark / GitHub Light Default palettes on Black / white): `src/theme/terminalColours.ts` resolves them and `setTerminalSettings` writes them into every terminal's Ghostty config. The palettes are the twenty presets' (`src/theme/presets/`) and the Ghostty themes with a licence the app may pass on (`src/theme/ghosttyThemes.json`, generated by `scripts/generate-ghostty-themes.ts`); the third-party notices carry each one's source and licence.

Settings › Interface also imports a local Ghostty theme file as a private terminal palette on the phone. The
existing document picker supplies a cache copy, read as text and then removed; unknown keys are ignored and no
command or remote content is loaded. Background, foreground and sixteen distinct ANSI entries are required.
`src/theme/importGhostty.ts` validates the file before the existing settings store saves the optional
`importedTerminalPalettes` list inside `settings.v1`; earlier settings remain readable without a migration.
Imports carry `origin: imported` with no licence fields, do not enter the bundled notices, and appear in both
existing terminal palette pickers. Importing does not select the palette or change any other colour or setting.
Selecting it uses the same terminal background, light-mode selection policy and native sync as a bundled palette.
