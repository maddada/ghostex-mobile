# Ghostex iOS Terminal Screen — Implementation Spec (for React Native reimplementation)

Extracted from `/Users/madda/dev/_active/Ghostex/iOS` (VVTerm fork). The terminal's colours follow the theme settings (palette, Terminal background, Terminal theme; see Backgrounds), and its keyboard follows the terminal's appearance. Terminal surface = native view; everything else described here is chrome to rebuild in RN.

---

## 1. Terminal Screen Layout

Source: `VVTerm/App/iOS/iOSContentView.swift` (`iOSTerminalView` @814, `iOSTerminalTabsBar` @2475, `iOSTerminalTabButton` @2547, `NavBarBackdrop` @2458), `Features/TerminalSessions/UI/Terminal/TerminalContainerView.swift`, `Core/UI/ServerTabChrome.swift`.

### Top-to-bottom structure

`VStack(spacing: 0)`:

1. **headerTabsBar** — merged into the header row: back button + tabs capsule track (fills the remaining width; no title text) + overflow button. Shown whenever ≥1 tab, including a single tab.
2. **sessionContent** — `TerminalEmptyStateView` (no sessions) or the active terminal container.

Screen sits in a nav stack with a native nav bar; back button hidden/custom. Zen mode hides tab bar + nav bar.

### Backgrounds
- Terminal view: ignores all safe areas. Its colours are the desktop's: the palette of the terminal's appearance (Terminal theme: Follow app, System, Light, Dark; palettes `terminalGhosttyTheme` / `terminalGhosttyLightTheme`, defaults GitHub Dark / GitHub Light Default), painted on the Terminal background (Black / white, Follow theme = the theme's work area, Custom colour `workspaceBackgroundColor` in both appearances). `src/theme/terminalColours.ts` resolves them; `setTerminalSettings` sends them to every open, warm and new terminal as Ghostty config lines (`Ghostty.ConfigBuilder`), with no reconnect and each session's font size kept. Light terminals use Ghostty's own selection colours (the desktop's adaptive selection); dark ones keep each cell's text colour on the palette's selection colour. The palettes offered are the twenty preset palettes and the Ghostty themes the app may pass on (`src/theme/ghosttyThemes.json`, see the README). A saved palette the phone does not carry (one dropped from the list) stays saved and is listed first in its picker; the terminal takes the colours of that mode's default palette (GitHub Dark / GitHub Light Default) on its Terminal background, so it stays readable (the desktop instead leaves an unknown name to Ghostty's defaults).
- Sessions view: the theme's sidebar colour for the saved appearance (`useAppearance().background`, the same colours as the drawer and Settings). Other: system background.

### Safe area

The screen (status bar area, header, the strip under the iPhone Duo's rail) paints the colour of what it shows: the terminal's background in the terminal, the chat's page in chat view; header ink, tabs and the status bar text follow that colour (dark ink over a light one). Height = top safe inset (fallback 44).

### Tab bar metrics (`ServerViewTopTabBarMetrics`)

- tabHeight 28, trackHeight 36 (fits inside the 44 header row), tabSpacing 4, trackInnerPad 4.
- Track: capsule background `primary.opacity(0.08)` + 1pt stroke `primary.opacity(0.12)`, clipped; flexes to fill the header between back and overflow buttons. Animations disabled.
- Layout: minTabWidth 120. itemWidth = (available - spacing)/count; ≥120 → equal-width row filling width. One tab, or a track not yet measured, also fills the width: a lone tab in a track narrower than 120 pt now fills it, its title ending in an ellipsis, where the earlier fixed 120 pt scrolling tab was clipped (a deliberate change, not "unchanged"). Otherwise a horizontal ScrollView (no indicators) whose tabs are sized so the next tab always peeks in (`tabStripLayout`, `src/components/terminal/tabStrip.ts`; so it is clear that the strip scrolls): as many whole tabs as still leave 25 % of the next tab showing, none narrower than 80 pt.
- Scroll mode: the edge that hides more tabs fades (`HorizontalFade`, the same component as the chat's pill rows, in the track's own colour over the header; left once scrolled, right while more follow). Only the active tab shows its close button in this mode, so a peeking tab shows its title, not a lone close button; wide strips and a single tab (which has no neighbour to hide) show a close button on every tab. Chat stays a header button, also in the narrow Duo status band.
- Scroll mode rests the active tab at the strip's start so the next tab always peeks in (`stripScrollOffset`); the last tab rests at the strip's end, where the previous tab peeks in instead. This replaces centring, which left a middle tab's neighbour only about 15 % visible. It happens on tap, on selection change, and after a close/content resize the offset re-clamps immediately (no stale gap at the end). The centering is owed again only when the active tab, the tab count or the track width changes; a manual drag ends it, and a re-render or reflow with the same active tab never undoes the user's scroll.

### Tab button

- HStack(spacing 8): status dot Circle 6×6 `statusColor` + title `.callout`, 1 line, primary.
- Padding: leading 14, trailing 36, vertical 7; height 36.
- Selected bg: `primary.opacity(0.18)` capsule; unselected clear.
- Close button overlaid trailing: `xmark` 11pt bold, `primary.opacity(0.92)`, 20×20 circle bg `primary.opacity(selected ? 0.16 : 0.12)` + 1pt stroke 0.12, trailing pad 8.
- Tap anywhere selects. Selection animation easeInOut 0.12s.
- statusColor: connected/open → NO dot; connecting/reconnecting → orange; disconnected/idle → secondary; failed → red.

### Dragging tabs and two sides (`src/components/terminal/tabDrag/`, `src/terminal/tabSplit.ts`)

- Hold a tab 300 ms, then drag (react-native-gesture-handler pan with `activateAfterLongPress`; a quick swipe still scrolls the strip and a tap still selects). The tab lifts (a copy 5 % larger follows the finger over the whole screen, its place in the bar empties), the bar's other tabs slide a tab's place to open a gap where it would land, and the strip does not scroll while a tab is held. Light haptic on lift and on a drop that moves the tab. Every phone size.
- Wide window (content at least `SETTINGS_LIST_WIDTH + SETTINGS_PAGE_MIN_WIDTH` = 695 pt wide, Settings' two-column breakpoint; the unfolded foldable, a tablet, a phone across), header on top, none of the iPhone Duo's panes, the screen in the chat view: the chat's right half is a drop zone (accent outline and wash, "Open side by side" near its top, stronger under the finger) for a tab with a chat view. Dropping there opens that session's chat beside the current one; at most two sides.
- Two sides: each side has its own tab bar over its own chat, the handle (a grip, "Show one pane") between them; tapping it puts every tab back in one bar, left side's tabs then right side's. A tab drags from one bar to the other (or onto the other side's chat), and a side left without tabs ends the split. The selected tab is the side the user touched last (its keyboard, its menus); the other side keeps the tab it showed. A side's Terminal View merges first (the terminal needs the whole screen).
- Order and split live with the tabs in the terminal store (in memory, as the tabs). A narrower window shows one bar in the same order and keeps the split for when it is wide again.

### Nav bar toolbar

- Leading: back chevron (`chevron.left`) → dismiss keyboard, then back.
- Principal: segmented view switcher (Terminal / Files / Stats / Sessions). For the RN v1 we have Terminal + Sessions.
- Trailing: one overflow menu (`ellipsis.circle`) holding both sections — the Agent Actions section (Rename, Sleep/Wake, Delayed Actions, Fork, Full Reload, Prompt Editor, Export Transcript) for resolved gxserver sessions, then the Session section:
  - "Send & Attach File" — `paperclip`; disabled unless connected + terminal view + not uploading.
  - "New Terminal" — `plus`.
  - divider, "Settings" — `gear`, "Find" — `magnifyingglass`, "Edit Server" — `pencil`, "Zen Mode", "Disconnect" (destructive) — `xmark.circle`.

### Connection status overlays (terminal area)

ZStack: bg color → terminal surface (hit-testing only when connected) → state overlay. States:

- Connecting: spinner + "Connecting..." (secondary).
- Reconnecting: spinner + "Reconnecting..." (orange).
- Disconnected: `bolt.slash` largeTitle secondary + "Disconnected"; optional caption "tmux session is still running on the server." or "Without tmux, app backgrounding can interrupt running commands."; Button "Reconnect" (bordered).
- Failed(error): `exclamationmark.triangle` red + "Connection Failed" headline + error caption; host-key failure adds "Trust New Host Key" (prominent); "Retry" (bordered).
- Initializing: spinner + "Initializing terminal..." ; init failed: "Terminal initialization failed" red.

### Banners

- Top warning: "Reconnecting…" / "Reconnecting (attempt N)…".
- Top warning (mosh→ssh fallback): "Using SSH fallback for this session." auto-dismiss 8s.
- Bottom info: "Installing tmux" / "Preparing persistent shell support." (v1: skip tmux/mosh installers)

### Empty state

Centered VStack(24): `terminal` icon 56 secondary; server name title2 semibold; "No terminals open" body secondary; button "New Terminal" (plus + text, pad H24/V12, tint bg, radius 10, white text).

### Alerts

- Closing a tab disconnects immediately by default. When "Confirm before closing tabs" is enabled, show "Close Tab?" → destructive "Close" / "Cancel"; message: `This will disconnect "<title>".`
- "Replace Trusted Host?" → "Cancel" / "Replace and Reconnect" (destructive); message includes host:port.
- "Upload Failed" → "OK".

### Floating controls (browse mode, phone)

Keyboard (`keyboard`), Upload (`paperclip`/`hourglass`), Enter (`arrow.turn.down.left`) buttons; spring response 0.28 damping 0.84.

## 2. Keyboard Accessory — the Befehlspad (command pad)

### Befehlspad (from the designs)
On iOS the floating Befehlspad replaces the "2 rows of keys" bar and the floating Upload button; Android keeps the bar ("Bar" below) as before the pad. Setting: Settings > Keyboard > "Command pad" (stored as `extraKeysToolbarVisible`, same meaning: on = pad toggle (Android: the bar), off = no pad and the round Upload / Keyboard / Refresh buttons as before).

- **Toggle** (four squares) by default bottom right of the terminal area, 16 pt in, 12 pt above whatever covers the bottom (keyboard, text editor, layer); with and without the keyboard; never in chat view. The pad stays open until the toggle is tapped again; closing it ends a layer and clears armed modifiers.
- **Moving it**: holding the toggle for 0.3 s picks up the whole pad (toggle, field, ring and modifier chip; a firm haptic, and a tick on the drop, both only with Key vibration on); it follows the finger and, let go, snaps to the side edge nearer to the pad's middle at the released height (a spring on the native animation driver, so it keeps going while the app's JavaScript is busy; the next drag takes the pad over from it; at once with Reduce Motion on, also when that is turned on while the spring runs). From the first touch on the toggle until that finger is up or its touch is cancelled, before and after the lift, the toggle keeps its touch: no other control of the screen takes it over (a pad key, a ring button, the edge swipe between tabs or a sheet's grabber under another finger do nothing meanwhile; React Native asks only the views above the toggle, and none of them claims a touch; the toggle also refuses React Native's responder hand-over, `cancelable`), and the swipe back to Sessions is kept from starting (both through `navigation.setOptions`: `gestureEnabled` off, which the native stack reads only as a touch begins, so it holds every touch that begins meanwhile but not the toggle's own, which began before; and an empty `gestureResponseDistance`, which the stack's full-width swipe reads as it is about to begin, after the finger has moved, so the toggle's own touch does not start that swipe; a tap turns the swipe off and on again at its release; a session switch or leaving the screen turns it back on as well; at every other time it works as before). UIKit's swipe from the screen's very left edge reads neither option once the touch is down; it starts only from a touch that begins in a band along that edge whose width the system does not publish, so the toggle on the left side stands 32 pt in from the pad room's left edge (16 pt on the right), which very likely keeps a finger on it out of that band; that it does cannot be shown from the code, only on a device. Lifted, only the finger that lifted it moves it, from where that finger was as the pad came up, so the up to 10 pt it drifted during the hold do not make the pad jump; a second finger neither moves nor drops it. A touch the system cancels puts the pad back where it stood and stores nothing, without the drop's tick: the lift ends with its own finger's end or cancel (`onTouchEnd`, `onTouchCancel` of the toggle), because the press's end does not tell the two apart. On the left edge the pad is drawn mirrored: the toggle sits 32 pt from the left edge (`PAD_LEFT_MARGIN`) with the field above it, and the four ring buttons and the modifier chip lie on the field's other side, towards the middle. The 3x3 field itself keeps its order (Esc, Up, Ctrl+C on top; every arrow points its own way). A tap shorter than the hold still opens and closes the pad. Only a drag stores a new place: a hold let go without one (the finger never more than 10 pt from where it went down, React Native Pressability's allowance for a held finger) puts the pad back where it stood, opens nothing and stores nothing, so a height a cover pushed it to never becomes its resting place. VoiceOver: the toggle's actions "Move to the left side" and "Move to the right side" (height kept). Allowed area (flat): the terminal area (below the header, above the home-indicator inset, and across only as far as the window's safe area: in landscape the terminal area runs under the screen's rounded corners and the camera, so the pad's side edges are 16 pt inside the safe area there, 32 pt for the toggle on the left) with 16 pt margins (32 pt from the left edge while the pad stands there), and only the part above whatever covers its bottom (+12 pt); the stored height is a fraction of the resting free range (`commandPadPosition.flat` in `settings.v1`, `{ side, height }`, 0 = top, 1 = bottom; absent or invalid = the default place), so the keyboard, the text editor and a layer never move the pad except to keep it above them, and it goes back when they leave. Geometry in `commandPadLayout.ts` (`padAnchor`, `padPlacementAt`, `padHeaderReach`, `padSideMargin`); the screen's `padArea` is the room it is given; the store and the hook are keyed by layout, `laptop` belongs to laptop mode.
- **Too little room for the open pad.** The open pad is 252 × 308 pt; with its margins it needs 340 pt of height with nothing covering the terminal area and 336 pt above a cover. Its keys never shrink to fit (52 pt keys, 44 pt ring buttons, 46 pt toggle). Where the area offers less:
  - **Over the header.** If the pad fits when it reaches over the header, it does: it stands just above the cover (16 pt above the bottom without one) and its top may rise into the header, at most to 16 pt below the window's safe area (`padHeaderReach`, with the header's room measured as the terminal area's top less the safe area's top). The header's controls are not used while typing on the pad. The pad is drawn in its own view over the terminal area and, while it needs it, the header (`TerminalScreen.tsx`), because the terminal area cuts off what lies outside it. This covers, from the measured frames: an iPhone 17 in landscape with the keyboard down (3 pt), and the text editor on the keyboard on the folded Duo upright (31 pt) and the unfolded Duo in landscape (26 pt).
  - **Keyboard down.** If it does not fit even then (a phone in landscape with the keyboard up: iPhone 17 178 pt short, iPhone 17 Pro Max 140 pt with its keyboard height assumed, the folded Duo turned 122 pt), opening the pad lowers the keyboard (as a layer takes the keyboard's place) and the pad uses the room with the keyboard down; the text editor, which rides on the keyboard, closes with it. Closing the pad brings the keyboard back. Because the open pad and the keyboard do not fit together there, asking for the keyboard while the pad holds it down closes the pad first: the ring's keyboard button closes the pad, which brings the keyboard back; the keyboard coming back another way (a tap on the terminal, the pen's editor) closes the pad as well and drops armed modifiers, as closing always does. The same holds wherever the keyboard comes up while the pad is open and has no room above it, even over the header, also when the keyboard was already down before the pad opened: a tap on the terminal, the ring's keyboard button, the text editor taking the focus or any other way closes the pad as the keyboard comes, drops armed modifiers, and leaves the keyboard up with the text editor on it if that was opening. Turning or folding the phone, or resizing the app's window, into such a pose while the keyboard is up and the pad open closes the pad and keeps the keyboard, dropping armed modifiers; turning back does not open the pad again. The pad wins over the keyboard only while the person is opening it. What the person asks for is judged at once (`openPadFitsAboveKeyboard` in `useCommandPad`), also while a turn, fold or resize is still settling: the iOS keyboard coming up from hidden (counted by the keyboard store's `appearances`, which a turn or fold of a keyboard that is already up does not change), the text editor opening on it. A keyboard request while a turn or fold runs with the keyboard up brings no keyboard up and belongs to the turn: the ring's keyboard button, which shows for a moment while the old keyboard frame lies outside the new window, or a tap on the terminal is judged with the turn's wait, up to 250 ms after its last report, and armed modifiers stay meanwhile. A turn, fold or resize is judged once it has settled: the system reports the window's new size, its safe area, the keyboard's new frame and the terminal area's new layout separately and in any order, and a mix of old and new reports can show too little room where the new pose has enough, or the reverse. So the pad's room is judged only after none of these has changed for 250 ms (`PAD_ROOM_SETTLE_MS`), from their latest values. Each report starts the wait again, so it bridges gaps of up to 250 ms between the reports of one change (expected to be a few frames, not measured on a device); reports further apart are judged as separate changes, so a report that comes more than 250 ms after the one before can close the pad and drop armed modifiers on a mix of old and new values although the final pose has room. Until then the pad stays as it was, with what is armed on it: where the new pose has no room, the open pad stays on screen, possibly cut off, until 250 ms after the last report before it closes, longer while reports keep coming. A request of the person that brings the keyboard up or opens the text editor during that wait is judged at once from the values reported so far and closes a colliding pad as it does without a wait, armed modifiers included; the wait goes on and judges the room once it has settled. A layout report of the terminal area that arrived after a newer one would count as the latest (React Native is expected to deliver layout events in the order of its layouts; not measured). Component tests take every order of the reports each change makes, back to back and 249 ms apart: an iPhone 17 turned to landscape (the pad closes), the Duo turned and folded both ways, and the keyboard growing taller (the pad closes) or shorter on the unfolded Duo. While a terminal area update is still settling, the keyboard brought up in landscape (a tap on the terminal, the ring's keyboard button, the text editor taking the focus) and the text editor opened on the unfolded Duo's 300 pt keyboard close the pad at once; the keyboard growing taller in that wait closes it 250 ms after its report, not 249 ms. The unfolded Duo's upright window and keyboard and the taller iOS keyboards are synthetic; none of this was run on a device.
  - **A Keys or Agent layer without room for the open pad.** A layer opened from the ring takes the keyboard's place with the keyboard's last height in that window (its own height before any keyboard was seen there). Where the open pad then does not fit above it, even reaching over the header, the layer takes the room. That is the case while the pad holds the keyboard down, and equally on a phone in landscape whose keyboard was already down when the pad opened (the pad fitted there with nothing covering the area, reaching over the header; above a layer of the keyboard's height it would lose its top row and all four ring buttons on an iPhone 17 in landscape, three ring buttons on the folded Duo turned). The pad is drawn closed, its toggle standing whole 12 pt above the layer, and armed modifiers stay armed with their chip beside it; the layer gets its own close button at the end of its head ("Close", a 44 pt target, `CommandPadLayer` `onClose`). That button, or a tap on the toggle, closes the layer and shows the pad again, and the keyboard stays down as it was: if the pad holds it, it comes back when the pad closes; if it was down before the pad opened, it stays down then too. Where the keyboard was up when the layer opened and a rotation took the room afterwards, closing the layer leaves the keyboard down as well and the pad now holds it, because the open pad and the keyboard do not fit together there: closing the pad brings it back. The keyboard coming back another way while the layer stands in for the pad (a tap on the terminal) ends the layer and leaves the pad closed, dropping armed modifiers, as above. Whether the pad fits above the layer is read from the room on every render (`padGivesWay` in `TerminalScreen.tsx`), so a rotation or window change that makes room (portrait, the unfolded Duo) shows the pad above the layer again, without the close button, and one that takes the room away hands the place back to the layer. The pad reappears at once with Reduce Motion on, otherwise it fades and grows out of the toggle as on every opening. Where the open pad fits above the layer, layers keep their behaviour and have no close button.
- **3x3 field** (52 pt keys) above the toggle: the user's nine keys (`commandPadKeys` in `settings.v1`, `settings/commandPad.ts`), default Esc / Up / Ctrl+C, Left / Enter / Right, Tab / Down / Upload. Keys send on touch-down through `sendKey` with the armed modifiers (one-shot / locked as below); arrows, Home, End, PgUp, PgDn repeat (350 ms, then 50 ms). A key activated without a touch (VoiceOver, Switch Control: a press whose event has no `changedTouches`) sends once on that press; the Keys layer's extra-keys pills do the same. Text actions, agent hotkeys (120 ms between steps), Paste (iOS: the terminal's own edit-menu Paste, `pasteFromClipboard`) and Upload (the source choice of the overflow menu's "Send & Attach File", Photo Library or Choose File, as the round Upload button; disabled without an open session or while uploading) act on release. Settings > Keyboard > Pad keys (Reset in the header) changes every position: keys, modifiers, KEYS-page shortcuts, Paste, Upload, and agent hotkeys and custom actions by reference, so their later edits follow (custom actions carry a stable id in `extraKeys.v1`, given on load to layouts saved without one). A deleted hotkey or custom action leaves its position "Not available": disabled, sending nothing until it is reassigned. A malformed stored entry (outside the id vocabulary), and Paste on Android (no native path, iOS-only scope), show that position's default key; a stored list that is not nine strings loads the default nine.
- **Glass**: toggle, keys and ring buttons blur the output behind them (`expo-blur`, as the design's frosted glass); with Reduce Transparency on they are opaque (`components/common/reduceTransparency.ts`). The glass tint follows the app appearance; the opaque backplates, docked layers and editor take model surfaces. Enabled key faces choose readable ink on their current fill over the terminal background; native blur remains a device-only contrast check. The docked layers are opaque panels, as in the design. Opening the pad fades and grows it out of the toggle (140 ms), at once with Reduce Motion on.
- **Ring** on an arc around the field: Keys (layer), Agent (layer; unavailable without agent hotkeys, only Codex, Claude Code and Pi have them; its accessibility hint then says that this session's agent has no agent hotkeys, and a tap on it shows the same sentence for the layers' hint time (3.5 s, `HINT_TIMEOUT_MS`), opening nothing: in a row of its own left of the toggle (mirrored on the left edge), above the modifier chips and below the field (`PAD_HINT_OFFSET`), reaching to the pad room's far 16 pt margin, so neither the chips nor any key moves and the line stays inside the window; where that row is too narrow for one line (narrower than any current iPhone) the sentence wraps upwards rather than being cut), Text editor (pen), Keyboard (show / hide). The keyboard button's symbol crossfades from show to hide over the keyboard's own motion (580 ms as it comes up, 250 ms as it goes, `keyboardMotion.ts`), at once with Reduce Motion on; its name changes with the keyboard. Opening or closing a layer gives the key bar's page-toggle tick (Key vibration). The optional round Refresh and Keyboard buttons stand above the closed toggle while the pad is at the right edge (moved to the left, they keep their own bottom right corner), and are hidden while the pad is open. While the keyboard is up and the pad closed, the round Keyboard button shows as Dismiss keyboard whatever its setting (Refresh stays hidden then), so one tap hides the keyboard; with the pad switched off it shows the same way among the round buttons. Where their column does not fit between its bottom edge and 16 pt below the terminal area's top (a phone in landscape with the keyboard up and the pad off: Refresh, Upload and Dismiss keyboard need 156 pt), the round buttons stand in a row instead, Dismiss keyboard nearest the corner.
- **Layers** take the keyboard's place (cross and ring stay put): opening one hides the keyboard, the layer gets the keyboard's last height in that window; the same button again restores what was there, the keyboard button or the keyboard coming up ends it. Where the open pad has no room above a layer, even over the header, the layer takes the pad's place instead and has its own close button (see "Too little room" above). Keys layer: "Extra keys" (the user's two rows below, unchanged behaviour) and "More keys" (the KEYS page), "Pad settings" opens Settings > Keyboard. Agent layer: the session agent's hotkeys. Page keys and hotkeys explain themselves while held. Absolutely at the window bottom.
- **Text editor** (the old editor page, below) rides on the keyboard in `KeyBarDock`; the keyboard going away closes it.
- **Laptop pose** (iPhone Duo half folded, `laptopMode.ts`; the laptop-mode design). There is no key row; the floating pad stays in the upper half (the open pad reaches below the fold only where the upper half is too short for it even reaching over the header, see below). Keyboard up or not (and with a Keys / Agent layer up) the terminal slides (grid unchanged, as with every keyboard) by everything below the fold's top and the area below it is covered in the terminal's background, so the output ends at the fold; when the cursor row stands higher than that slide allows (cursor wins), the view slides less, the cursor row stays at the area's top and the view's rows below the fold's top are covered, not moved (the view's own frame then reaches below the fold). Touches on the covered part reach no terminal; a tap on the output above the fold brings the keyboard. The pad's room (`padArea`) is the part of the terminal area above the fold's top, in every state of the pose the room it is placed, moved and judged in: its default place is bottom right, with the toggle 44 pt (a finger's width) above the fold, which is also its lowest place there while the text editor is closed (a stored place lower than that shows at it and stays stored as it is); it moves only there (drag, VoiceOver moves), its place is stored as `commandPadPosition.laptop`, mirrored on the left edge as flat. The keyboard and the layers lie below the fold, so they never move it: a layer opens below the fold in the keyboard's place with the keyboard's last height, never closer than 8 pt to the fold (`laptopLayerHeight`), cross and ring stay put. The text editor stands 12 pt above the fold (the terminal ends above it) and is the only cover in the pad's room: where the open pad fits above it (with a one-line editor it needs 404 pt between the area's top and the fold), the pad stands 12 pt above the editor; where the upper half is shorter (expected on the Duo's inner display, not measured on the device), opening the editor closes the pad by the rule for too little room above the keyboard, the closed pad's toggle stands 12 pt above the editor, and Send (text sent, editor closed, the keyboard handed back to the terminal) or a tap on the toggle (editor closed the same way, the keyboard stays up) opens the pad again (`openOverEditor`); the editor's own close button (below, "The text editor rides on the keyboard") closes it as the pen does and leaves the pad closed. Reaching over the header applies to the pad's room unchanged. Lowering the keyboard would add no room in this pose, as the keyboard lies below the fold, so opening the pad never lowers it here: where the upper half is too short for the open pad even reaching over the header (without the editor; not expected on the Duo's inner display, not measured on the device), the open pad's room reaches below the fold's top by exactly what is missing (`laptopPadRoomBelowFold`). The open pad then reaches over all of the header, its top 16 pt below the safe area's top, and its lower edge stands where the room's bottom less the toggle's 44 pt lowest place puts it (an upper half of 340 to 368 pt, where the pad fitted while that lowest place was 16 pt, now takes this room too); nothing of it is cut off. The keyboard stays up as the pad opens, and neither the keyboard coming up nor a fold into such a pose with keyboard and pad up closes the pad. Closed, the toggle stands in the upper half again, 44 pt above the fold. A Keys or Agent layer below the fold that keeps the pad's usual 12 pt below it leaves the open pad as it is; a layer that comes up further into the pad's room takes the place as above: the pad is drawn closed with its toggle in the upper half, the layer gets its own close button, and closing the layer shows the pad again, the keyboard staying down as in that rule (`laptopPadReachBelowFold`). On an upper half shorter still, where the pad reaching below the fold would reach the keyboard's top, the pad reaches there as well and the keyboard covers its lower part; that geometry is not handled. With the pad switched off, or with its closed toggle on the left edge, the round buttons stand 44 pt (a finger's width) above the fold, keyboard up or not, so a thumb presses them clear of the knick (`laptopFloatingBottom`); above the open text editor they stand 16 pt above it, and with the toggle on the right edge 12 pt above the toggle. Connection overlays (Retry, Reconnect) stand above the fold. In chat view the transcript and the composer end above the fold, keyboard up or not: with the keyboard down the chat view ends 8 pt above the fold's top (`foldUpperHalfInset`, `chatFoldInset` in `TerminalScreen.tsx`) and the lower half stays empty; with the keyboard up the chat keeps its area and the composer lifts itself to 12 pt above the fold (`KeyboardLiftedView`). Other poses (flat, book pose, other iPhones, Android) are unchanged.

### Attachment

Real `inputAccessoryView` riding above the software keyboard. Hidden when: hardware keyboard attached, find navigator active, or browse mode.

### Keyboard: the terminal slides, the grid stays (iOS, terminal view)

Decided on the report that the terminal jumped when the software keyboard came and went; the slide rule below replaced an earlier one, on the report that the keyboard covered the question card omp draws in the terminal below the cursor. Cause, as found in the code: the screen shrank the terminal container by the keyboard height at once (`TerminalScreen` bottom padding), so the native view's bounds changed, `sizeDidChange` set a new surface size and `onResize` announced a new grid to the host, whose pty resize made the remote program redraw; the keyboard's own animation was not used (`useKeyboardMetrics` read only `endCoordinates`). Not reproduced on a device; the redraw part is an inference.

- **The grid stays.** On iOS in terminal mode the terminal view keeps the size it has with the keyboard hidden (the area above the home-indicator inset), whatever the keyboard, QuickType, the pad's text editor or a pad layer do: no surface size change, no `onResize`, no grid announcement caused by them. Rotation, fold and window-size changes still resize it as before. Chat view and Android keep their paths (Android: container padding, key bar in the flow).
- **The view slides.** The terminal area clips its content (`overflow: hidden`); the view moves up by `terminalSlideOffset` (`terminalKeyboardSlide.ts`): always as far as the bottom row stands directly above what covers the view's bottom (the keyboard, the text editor riding on it, or a pad layer in the keyboard's place), so what the program draws below the cursor (an omp question card with its options) is visible; only when the cursor row would then leave the top of the visible part, as far as it stays visible. With `caretTop` the cursor row's top edge and `obstruction` the covered height: `offset = clamp(min(obstruction, caretTop), 0, obstruction)`; cursor row in the lower part: the whole covered height; cursor row near the top (`caretTop < obstruction`): `caretTop`, the cursor row at the visible area's top edge; nothing covering (keyboard hidden and no layer) or view not laid out: 0; no cursor row reported yet: the covered height (the bottom is visible, no known cursor can be lost). The covered height is the larger of the keyboard's overlap (window height less the reported frame's top) plus the open text editor's height, and the frame of an open pad layer (the keyboard's last height in this window, or the layer's own height before any keyboard was seen), less the home-indicator inset below the view; with a layer and the keyboard hidden it is therefore not 0. No extra gap is added on iOS (the 3 pt gap is Android's). Rows moved above the area are hidden behind the header while something covers the bottom; scrollback still works.
- **The cursor row** comes from the native view's `onCaretChange` (`{ top }`: the cursor row's top edge in whole points from the view's top, `y - height` of `ghostty_surface_ime_point`, where Ghostty's `imePoint` (v1.3.1) sets `y` to the bottom of the cursor cell with the padding included and `height` to the cell's height; sent after a draw when the whole-point value changed, and once when the view is attached), so the offset follows new output and a growing prompt. iOS only; the Android view declares no such event and the prop is not passed there.
- **With the keyboard's animation.** The shared keyboard store (`keyboardFrame.ts`) requests `LayoutAnimation` before it publishes the frame that changes the overlap; `useKeyboardMetrics({ slides })` reads the store and requests nothing, so the terminal's offset, the pad's position and the text editor are expected to move in step with the keyboard (basis and limit below); a repeated report of the same frame (`keyboardWillShow` and `keyboardWillChangeFrame` for one move) animates once. The motion is an approximation of the system's: React Native's Fabric renderer (0.88) has no keyboard curve (`LayoutAnimation.Types.keyboard` falls through to linear there), and linear looked wrong on the device, so the screen asks for configs fitted to the measured keyboard motion, defined once in `components/common/keyboard/keyboardMotion.ts`: a show (the keyboard's top appears or rises) is a spring, `springDamping` 1.8, 580 ms (rmse 5.6 pt, worst 14 pt against the recording; linear over 250 ms was 20 / 49 pt); a hide (the top leaves or lowers) is an ease-out, 250 ms (rmse 13 pt, worst 27 pt; linear 33 / 58 pt). Basis: one screen recording (iPhone Duo inner display, iOS 27.2, 60 fps, 6 shows and 5 hides), one device; the hide is only visible for about 0.17 s, so its fit is weaker. Not identical to the system curve; the approximation was chosen over the exact approach, react-native-keyboard-controller, which is a separate change. The event's `duration` is no longer the length (what iOS reports there was not measured and the fit needs 580 ms); it only decides whether to animate at all (0: nothing). `LayoutAnimation` is app-wide and last-writer-wins, so on iOS the shared `keyboardFrame.ts` store is the one writer for everything that follows the keyboard, the terminal included: `useKeyboardMetrics` registers no keyboard listener of its own there and reads the store (`useKeyboardState`), so the terminal's layout change is expected to land in the render the store's publish causes; one request per keyboard move. The store's visibility model: the keyboard is visible between `keyboardWillShow` (iOS posts it for every appearance) and `keyboardWillHide`; `keyboardWillShow` is never discarded (it always means visible, and requests the show motion when the keyboard appears or its top changes); a `keyboardWillChangeFrame` while hidden (the end frame of a hide) is ignored; one while visible updates the frame and requests show (end top above start top) or hide (below), read off the notification's own `startCoordinates` and `endCoordinates` (one coordinate space, so a turn or fold cannot skew it; the stored frame only when a notification has no start frame); one whose end frame starts at or below its start frame's bottom edge is a frame-only hide (hide motion once, hidden; the later `keyboardWillHide` finds it hidden). An appearance is counted only from hidden. The terminal additionally masks the store's visibility with the current window (`keyboardTopInWindow`). The store counts appearances, so a terminal mounted while the keyboard is up sees none. The chat composer's lift (`useKeyboardInset`) follows the same fitted motion as a consumer of the store (`useKeyboardTop`) too: no keyboard listener and no animation request of its own, no measurement at keyboard time. Its overlap is its resting bottom edge in the window (cached from its layout: `onLayout`, and again when the window's height changes; the window's bottom until the first measurement) less the keyboard's top, so the composer, and what sits above and below it, are expected to change in the render the store's publish causes, with the store's one request, and nothing with Reduce Motion or a zero duration. Basis and limit of that expectation: React flushes the sync-lane render from the store's publish in a microtask after the keyboard event, so a JS-driven `Animated` frame (a later task) should not land in between; a `setNativeProps` or `Animated` update made synchronously inside another keyboard listener could still consume the pending Fabric config (the store holds the only iOS keyboard listeners in `src`; no code sets such values there); the device hand test decides. Reason (screen recordings of an installed build; cause inferred, not proven): its own request came after an asynchronous measurement (show) or after the store's commit (hide), so another commit could consume the pending config and the composer's own change landed unanimated, while the row below it slid. Its geometry (padding = inset + 8, `inputMaxHeightFor`) is unchanged. This also changes the `keyboardFrame.ts` motion for its other consumers (`VerticalBarArea`, `KeyboardAvoidingContainer`, `BottomSheet`, the chat sheet, `fieldReveal`, `FindPromptsScreen`, `SessionSearchSheet`): they follow the keyboard more closely too. Cursor-row moves are not animated. A pad layer opening or closing with the keyboard hidden is not animated (no second `LayoutAnimation` writer); with the keyboard up it takes the keyboard's exact place: replacing the bare keyboard moves nothing, but when the text editor is open, opening a layer closes the editor, so the editor's height leaves the covered height and the terminal moves down by it (for example offset −358 → −302 pt).
- **Reduce Motion.** With the system setting on, one carrier (`components/common/reduceMotion.ts`: `AccessibilityInfo.isReduceMotionEnabled()`, followed through `reduceMotionChanged` while anything consumes it; read from React by `useKeyboardMetrics`, from the non-React keyboard store by `isReduceMotionOn`) is the only source, and the one writer of the app-wide `LayoutAnimation` on iOS, the shared `keyboardFrame.ts` store (mounted by `VerticalBarArea` for the whole app), requests none (`useKeyboardMetrics`, the sheets and the chat composer request nothing of their own). Consequence outside the terminal: the other consumers of `keyboardFrame.ts` no longer animate their keyboard moves with Reduce Motion on either (a deliberate change to the earlier behaviour). Then the terminal's offset, the pad and the text editor go to their end positions at once, the editor unmounts without the hide delay and the pad opens without its fade. Geometry and end states are the same.
  A change event takes precedence over an initial preference read that is still pending; stopping observation also invalidates that read.
- **Keyboard summoned while scrolled back.** When the keyboard comes up (hidden to shown; keyboard button, tap or focus alike) the terminal is scrolled to the bottom of its scrollback (`GhostexNative.scrollToBottom`, once), so the input area is visible above the keyboard (and the text editor when open). Not on a frame change while the keyboard is already up, not in chat view, not on Android. On iOS "comes up" means the reported frame reaches into the window: a `keyboardWillChangeFrame` that ends below it (after a hide) counts as hidden, so it neither scrolls nor keeps the editor, and the pad goes back to its resting place. Only the terminal on screen scrolls (`mountedTerminalSessionKey`: open tab, not chat view, screen focused): a retained terminal behind another screen that opens its keyboard (Settings text input) keeps its scrollback; the layout predicate `slidesWithKeyboard` does not depend on focus. The cursor row's `top` is the active area's (Ghostty's `imePoint` does not depend on the scroll position), so the offset needs no recomputation after the scroll.
- **The text editor rides on the keyboard.** On iOS the pad's text editor is in `KeyBarDock` (as the key bar was before it), absolutely positioned across the window width, `inset` points above the window's bottom edge while the keyboard is up and below it while it is away; it stays mounted for the hide motion's 250 ms (`KEYBOARD_HIDE_MOTION`; 0 with Reduce Motion) so it leaves with the keyboard, then unmounts and is out of touch and VoiceOver reach while leaving. Its draft belongs to its session and is kept in the terminal store (`textEditorDraftBySessionKey`), in memory only: however the editor closes (the pen, the keyboard going away, the pad toggle lowering the keyboard, a Keys or Agent layer taking its place, a session switch, leaving the terminal screen), the next opening for that session shows the draft again; only Send empties it, and it is not kept across a restart. While the editor is open and the pad is closed because the open pad has no room above the keyboard and the editor, even over the header (a phone in landscape; the laptop pose where the upper half is too short for the pad above the editor), the pen is out of reach, so the editor has its own close button at its end, the layer's from "Too little room" above ("Close text editor", a 44 pt target, `TerminalTextEditor` `onClose`, read from the room on every render), which does what the pen does: it closes the editor, keeps its draft and leaves the keyboard up, and the pad stays closed; where the open pad fits, the editor has no such button. The editor is keyed by session and reads that session's draft as it opens, so a draft never reaches another session's terminal. The pad needs no optimistic state after a tap: its toggle follows the keyboard's overlap (the optimistic bar, `tapKeyboardHint`, serves Android's bar). The pen hand-over and the hardware-keyboard behavior are unchanged; with the pad switched off, the floating controls are lifted by the keyboard's overlap so they stay above it.
- **One place to restrict it.** `slidesWithKeyboard` in `TerminalScreen.tsx` (`Platform.OS === 'ios'`, with two panes always, else not in chat view) decides it for all iPhones; limiting it to the iPhone Duo would change that line only.

## 3. Pinch to Zoom

- Pinch recognizer on terminal surface; disabled while text selection active.
- Changes **font size in points**, per-session. Range 4.0–32.0, step 1.0. Default: 13pt.
- Ratchet logic: reference scale at began; relativeScale ≥1.12 → +1pt; ≤0.89 → −1pt; reset reference each step. Not continuous.
- Persistence: per-session presentation override, persisted; falls back to global `terminalFontSize`.
- HUD: centered dark-blur card radius 18, min 112×72; value "12 pt" (monospaced 24 semibold white) over "Font Size" (12 medium white α0.72). Fade in 0.12s, auto-hide 0.8s idle (0.45s after gesture end), fade out 0.18s.

## 4. Scrolling

- iOS: NO native scroll view. Single-touch pan → synthetic scroll events into the terminal engine, `translation * 4.0`, precision, reset translation each change.
- Momentum: if |velocity| > 35 → per-frame v = velocity/60 * 4.0 * 0.75, display-link ticks, decay ×0.94/frame, stop at |v| < 0.5, send momentum began/changed/ended.
- New pan/pinch stops momentum. Scroll-to-bottom on output/keypress handled by the engine. No scrollbar, no jump-to-bottom button.
- Android note: Termux TerminalView has its own scroll/fling handling — keep it; pinch-zoom must map to font size changes like iOS.

## 5. File Attach & Send

- Entry: overflow menu "Send & Attach File" (paperclip), the floating Upload control and, on iOS, the Befehlspad's Upload key. Enabled only when connected. Each asks for the source first: "Photo Library" / "Choose File" / "Cancel" (on iOS the menu row waits for the menu to finish closing).
- Picker: "Choose File" opens the document picker, any type, single selection; "Photo Library" the photo library, images, single selection.
- Payload: read file data, filename (fallback `upload.bin`), MIME (`application/octet-stream` fallback), isImage by UTType/MIME.
- Remote path creation (run over SSH, POSIX only):
  ```sh
  tmp_base="${TMPDIR:-/tmp}"
  attachment_dir="${tmp_base%/}/ghostex-ios-attachments"
  mkdir -p "$attachment_dir"
  tmp_path="$(mktemp "$attachment_dir/upload-XXXXXX")"
  target_path="${tmp_path}-<sanitizedFilename>"   # sanitize to [A-Za-z0-9._-], others → '-'
  mv "$tmp_path" "$target_path"
  printf '%s\n' "$target_path"
  ```
- Upload via SFTP (or exec-preferred on Darwin), permissions 0600. Delete remote file on failure.
- On success insert into terminal (no trailing newline): `[<title>](<remotePath>)` where title = "Image #N" / "File #N" (per-kind counters).
- Progress: icon flips to hourglass + disabled; failure → "Upload Failed" alert. Not-connected error copy: "Reconnect the terminal before uploading files."

While the chooser is one of the two panes neither moves: it is a picker, never stored, so no title bar drags and there is no grip.
- **Divider.** Its 44 pt handle stands in the gap only while the keyboard is down (and no Keys or Agent layer stands in its place); half folded like a laptop the fold alone does not hide it. Dragging it resizes both panes, clamped so each keeps 25 to 75 % of the pane container (the terminal area below the header); while dragged it shows both shares ("60 % · 40 %", with "limit" at a bound). The panes follow the finger once per frame, its newest position, while each terminal keeps its size until the drag ends. Letting go takes effect at the next frame too: the new position is stored and each terminal is handed its new size once, at that frame (each new size measures the terminal's grid again and resizes the computer's terminal for every row gained or lost). Losing the touch (the system cancels it) discards the drag: at the next frame the panes show the position they had before it again, nothing is stored and the terminals keep their size; a pane without a terminal is not drawn again while only its size changes. VoiceOver: adjustable in 5 % steps. Only the user's drag or adjustment of the handle is stored, per window shape.
- **Half folded like a book** (the fold down the turned inner display) the panes have no layout of their own: the slots, the cards, the terminals' sizes and the stored divider stay as they are, and the content may run across the fold, but nothing to touch stands on it. A handle that would stand on the fold stands beside it, on the divider's side, in the title bars' row (no terminal's content there); each title bar keeps off the fold and the handle, giving up the side of its card nearer to them, so its grip, title and close button stay together. The controls in a pane without a terminal keep off the fold the same way, giving up the side of the body nearer to it, wherever the divider stands: the Web Preview's start and its page's toolbar and Retry, the Files search row and failure card, the Changes scope row, scope menu and failure card, every row of the chooser, the agents pane and the attention list, and the usage pane's head (Refresh) and accounts; the page, the file tree and the changes may run across it. The queued-prompts pill in the selected session's pane starts past the fold when the fold lies in the leading half of that pane's body, where the pill stands.
- **Keyboard** (nothing of it is stored): upright with the top pane active, both keep their slots and the bottom pane ends at the keyboard, down to its title bar (a top pane that does not fit above the keyboard ends there and the bottom pane is its title bar); upright with the bottom pane active, the divider moves up as far as the bottom pane needs to keep 240 pt above the keyboard; across, both panes end at the keyboard; half folded like a laptop, both panes end 6 pt above the fold, where the keyboard and the layers below it do not reach them. When the keyboard hides, the divider is back where the user set it. Each terminal keeps the size its pane has without the keyboard (its grid stays) and slides over what the rules take from it, as the full-screen terminal does (§2).
- **Text editor and pad.** Upright the text editor rides on the keyboard across the window and counts as part of the cover; across and half folded it stands over the active pane only, as wide as it, and only that pane's terminal ends above it: half folded, what covers the window below the fold does not reach up to the editor, so the other pane keeps its output down to its end. The pad keeps its place and its room over the whole pane container, as with one pane (§2, also its laptop-pose rules), and acts on the active pane.
- **Closing.** A pane's close button leaves the other pane alone on the full screen (it takes the selection when the active one closed); with a session pane beside a pane without a terminal (the chooser too), either close button leaves the session. Closing applies to every window shape (upright, across, half folded like a laptop): no shape opens panes by itself, nor do the panes last on screen come along when the window turns, until the Panes button opens them again; each shape's pane types and divider stay stored and come back with that open, a session shown before does not (Panes button, above), and a chooser opened there (with nothing stored for the shape, or in place of a stored session) keeps the panes closed until a session or a pane type, such as Web Preview, is picked in it. A session's tab closing (closed, killed, slept, evicted) ends every layout whose session pane shows it; a Files, Git Changes or Usage pane opened from that session stays.
- **Window shapes and restart.** Upright and across each keep their own layout. Turning into a shape with nothing stored for it brings the two panes on screen along, the divider in the middle, and stores them for that shape (not after closing, above). Turning into a shape with a stored layout while panes are on screen (the chooser one of them, too) opens it as the Panes button does: the selected session where its first session pane was, its other pane types and divider as stored, the chooser in place of a second stored session; that chooser's close button closes the panes in every shape, the session staying. The layouts are stored in `panes.layout.v1` (AsyncStorage, exactly the pane-layout schema version 1, with `"closed": true` while the panes are closed; a value without it reads as open); a stored value that is not exactly that, or shows one session in two session panes, is discarded and one pane is used. After a restart the stored second session is attached again without changing the selection; one whose computer is no longer known leaves one pane. Development builds show the stored upright layout in Settings › Advanced ("Pane layout, upright (debug)").
- **Gestures.** Only the title bars and the divider handle take a drag; a gesture that starts in a pane's content is the terminal's (selection, scrolling, pinch) and never moves or resizes a pane. The panes' bodies keep clear of the handle's touch area.
- **The other pane types.** The chooser lists them under "Show in this pane" above its sessions; the title's pane type menu lists Session, Web Preview, Files, Agents, Git Changes, Usage and Attention and sets the pane's type, the other pane keeping its content (and its terminal). Files and Git Changes are offered only for a session with a project folder (as the ⋯ menu's Files and Changes); the only session pane offers no other type (the selected session is always a pane's); Session on another pane opens the chooser there, and so does the checked Session of a session pane beside another session pane (VoiceOver hint "Opens the session choice for this pane"): that chooser lists neither session on screen, a pick replaces that pane's session and is stored, and Close brings the pane back with its session, the selection staying on a session on screen. A picked pane becomes the active one.
  - _Web Preview_: the existing Web Preview of the selected session's computer, its start (address, listening ports) and then the page, with one row of Back, Forward, the address, Reload and "…" (Desktop Site, Open in Browser; Forward then Reload move into "…" below 340 and 240 pt). Back at the first page returns to the start. Its title is the page's address.
  - _Files_: the Files browser (`DocsBrowser`) of the project; a file opens in the full-screen viewer, except an HTML file that declares itself a Ghostex page, which opens as its page in the full-screen Web preview (`openComputerPage`, as from the Files screen); Add to Session Context fills the session the pane was opened from, in the view that session shows: while it stands in a session pane on screen the view its pane shows (terminal or chat, the pane's own choice), otherwise its saved view.
  - _Git Changes_: the read-only Changes view (`ChangesView`, `runGitAction changesDiff`); a tap on a changed file shows its diff in the pane; no stage, commit or revert.
  - _Agents_ ("All sessions with their status"): the selected session's computer's agent sessions from its session list (the app's one summary poll): the counts with a question, working, done and failed ("2 working"), each beside its status dot, then the sessions by project, each the chooser's row (agent icon, title, agent and status in words). A tap opens that session in the session pane as a terminal. Its title is "Agents".
  - _Attention_ ("Notifications from your agents"): the Notifications screen's list (`AttentionList`) of every computer, read again when the pane comes into view, with its row menus and pull to refresh. A tap opens the row's session in the session pane as a terminal and marks the row read; an account row only becomes read. A "has a question" row opens the session's chat view at its question card, full screen, as from the Notifications screen (the session is in the computer's list, so the card is there at once); the panes wait while it stands, and the Panes button is not there. Back there (the header's Back, or its entry in the side bar) goes back to the panes as they were: the session that was beside the list is selected again (a question of that session itself shows its terminal again), with the stored types and divider; if that session's tab has closed meanwhile, Back goes to Sessions as usual. While that chat view stands, the stack's swipe back (iOS) is not offered, as it would leave for Sessions past the waiting panes: Back is the way back there; once the chat view is left, the swipe is offered again. Back and the swipe back in a chat reached any other way (the Notifications screen, a notification) still go to Sessions; a question opened that way stands full screen as well (above, "Chat in a pane"). Switching the chat to the terminal view (or to another tab) also brings the panes back, the session pane showing the selected session. Its title is "Attention".
  - _Usage_ ("Claude and Codex limits"): the chat Accounts panel's head ("Accounts & limits", Refresh) and, per saved and enabled Claude or Codex account of the computer, its logo, name and email over its meters, three to a line: the window's name and percent over a thin bar and "↻" with the time to its reset. The bundled chat core's handle-free `accountUsageColumns` supplies the columns; the Accounts panel's shared `UsageRow` draws them with the app surface's appearance roles. Identity and filtering remain in the pane. A login without usage says "Usage is unavailable for this login." (never a bar at 0 %); what the computer says about reading it stands above. Read through gxserver's `agentAccounts` (`operation: "list"`, no chat session needed) when the pane or the Usage screen opens, every 30 s while it stays open (also while another screen covers it), and with `refresh` on Refresh; one read at a time: while an answer is out (up to a minute) the next poll waits for it, so a slow answer or a failure shows when it comes; a failed read, including a core-page failure, keeps what was shown and says why; no enabled account (none saved, or all turned off): "No Claude or Codex account is enabled in Ghostex on <computer>. Enable or add one there …". Its title is "Usage · <computer>".
  - Files, Git Changes and Usage stay with the session they were opened from: the slot's own session when a session pane is switched, else the selected session; selecting other sessions (also of another computer) never changes them, and that session's tab closing leaves them. Files and Git Changes show its project and are titled by its name; Usage shows its computer. Stored as `{paneType, sessionKey: <origin session>}`; the browser, agents and attention panes as `{paneType}` (the browser's page is not stored: after a restart it shows the start; the agents pane follows the selected session's computer, the attention list spans every computer). A stored files or Git Changes pane whose session the computer no longer lists says so; a usage pane whose computer the app no longer knows leaves one pane.
  - With such a pane active there is no pad, no floating terminal buttons and no text editor (their keys would reach no terminal); it becoming active takes the keyboard from the terminal. The queued-prompts pill stands in the selected session's pane. Closing either pane of a session and such a pane leaves the session alone. Folding while such a pane is active opens its content full screen (Web Preview at its page or start, Files, Changes, the Notifications screen, the Usage screen of its computer; for Agents the Sessions screen, the full-screen list of a computer's sessions, which the terminal's Back opens, switched first to the agents pane's computer; its workspace filter stays its own); unfolded the layout is back on the terminal screen.
